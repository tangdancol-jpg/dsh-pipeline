# 文件规模体检（大小是信号，不是死限；为拆而拆没有意义）

> 本文档回答一个问题：**"不写大文件"这条规矩，机器该管到哪一步？**
>
> 结论先说：**机器只报告，不做判决；也不建任何登记表。** 大小是信号；"该不该拆"必须像正常
> 程序员那样判断 —— 看职责是否单一、命名能不能一句话说清、评审能不能看出边界、并行改动会不会打架。
> 把行数做成"超 400 就红"的硬闸是死限思维；把大文件逐个登记成"基线"会催生"为登记而登记"。
> 两者都被用户否掉了；本设计是第三版，也是最薄的一版。

- 状态：**已实现（报告版）**
- 代码：`tests/file-size-check.mjs`（登记在 `tests/registry.mjs`，`run-all` 每轮跑）
- 执行点：`tests/run-all.mjs` + `docs/release-checklist.md` §6b
- 目录约定：规则设计档放 `design/conventions/`；体检放 `tests/`（一测试一文件）

---

## 1. 判断标准（真判据，在人和评审手里）

拆不拆，按顺序问四个问题（`CONVENTIONS §4` 原文）：

1. **改动原因是否单一？** 这个文件会不会因为两件不相干的事同时被改？
2. **能不能一句话命名？** 文件名是否说清了它负责哪一件事？
3. **评审能不能一眼看出边界？** diff 落在哪一块、会不会顺手改到别人地盘？
4. **并行改动会不会冲突？** 两个 AI/两个人同时改它，是否必然撞车？

四问里有任何一个答不上来 ⇒ **应该拆**。四问都过 ⇒ 它多大都可以留（例如单一声明表、
生成物里的常量表、状态迁移表、宿主单入口）。**行数只在"看一眼"时用**：超过预警线（400 行）时，
先照着四问自检一遍；拆不拆由作者判断、评审复核。**为拆而拆、为凑线删注释，都没有意义。**

---

## 2. 机器做什么（只有一件事：出一份报告）

`tests/file-size-check.mjs` 扫一遍 `index.js / lib / presets / tools / tests`，输出：

- 扫描到的文件数、总行数、最大文件；
- **超过预警线（400 行）的文件清单**（按行数降序，最多列 25 个）；
- 一句话判断依据（§4 四问）。

它**永远全绿**：不判红、不阻塞、不设上限、不设基线、不建登记表。
报告跑完落在 `tests/last-run.txt`（由 `run-all` 统一收集），人看一眼即可。

### 为什么连"基线/登记表"都不建

- 登记表会把"判断"退化成"填表"：新文件为了不红去登记，老文件为了不超线去删注释；
- 想观察"某个文件是不是又变大了"，`git diff` 与评审比登记表更直接、更可信；
- 少一个需要维护的数据文件，就少一处会漂移、会过期、会被人当作"豁免名单"的东西。

## 3. 扫描范围

`index.js`、`lib/**/*.js`、`presets/**/*.js`、`tools/**/*.{js,mjs}`、`tests/**/*.mjs`；
跳过 `node_modules`、`.git`、`.pipeline`、`generated`、`design`、`docs`、`locale`、`skills`、
`examples`、`types`。

不扫数据文件（JSON 表、schema 表）：声明表不是"该拆的逻辑"（与 §4 ① 同口径）。
也不扫运行期生成物与任务交付物。

---

## 4. 与 CONVENTIONS 的关系

| CONVENTIONS | 本体检怎么落 |
|---|---|
| §4「新增文件 ≤400；超了先自证」 | 报告里有行数；作者按 §1 四问自证，写不出就拆 |
| §4「不许为凑行数把同一件事切碎，也不许塞满」 | 报告只给事实，**不奖励拆小**；凑线形状由评审看 diff 判断 |
| §5「既有大文件不许再堆；>500 行先抽取再改」 | 报告列出大文件；增长情况由 `git diff` 与评审看，不靠机器盯 |
| §4「一个文件一个改动原因」 | 机器判不了，**这就是为什么只报告** |

## 5. 历史与已知限制

- 第一版（commit `fcfa934`）：硬闸（四类红 + 390–400 禁用带 + 只降不升）—— 被用户否掉：
  "大小不是死限，应该像正常程序员一样判断"；
- 第二版：预警 + 88 条基线登记 + 登记卫生红 —— 被用户否掉："为拆而拆是没有意义的"；
- 第三版（本设计）：只报告、不判红、不登记 —— 最薄，也最不容易制造反向激励；
- 机器**判不了职责**：拆得碎（同一职责切三份）、边界错（两个职责混着）它都看不出来；
  这类问题靠 §1 四问 + 评审；
- **不监控运行期生成物**与任务交付物（席位的项目代码）；若以后要管，应走
  `pipeline_change_audit` 那层单独设计，不混进本体检（混进来判据就不纯了）。
