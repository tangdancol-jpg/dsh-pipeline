# Stop Ladder · 停一下，过四问

> 这份 Skill 是**引导**。真正的拦截在 `dsh-pipeline` 插件的代码里
> （`tools/pre-execute` / `agent/pre-step` 两个宿主拦截缝 + 工具守门）——
> 越界的能力在那一层**直接不给**。四问的作用是让你**别走到被拒那一步**。

## 什么时候用

在你**准备做一件计划/需求里没有明确要求的事**的那一刻。典型触发词：

- "顺手也把它改了" / "顺便统一一下风格" / "这里其实应该抽象一下"
- "版本有点旧，顺手升一下" / "加个配置项更灵活" / "补个防御性判空"
- "用户应该会想要这个" / "以后可能用得上" / "这样更优雅"

**不用它的场合**：需求/任务卡里明确写了的事。四问不是让你怀疑任务，是让你怀疑**自己的加戏**。

## 四问（逐条判，答不上来就是不做）

### ① 用户让你做了吗？

**怎么判**：找出**具体那一行**依据 —— 需求原文、任务卡的验收标准、计划里的 `change_scope` 条目。
读出来，指给谁看都行。

- 找得到 ⇒ 继续问 ②。
- 找不到 ⇒ **停**。"我觉得应该"不是依据。

> 这一步在插件里有对应判据：编写只能改 `change_scope` 授权面内的路径，
> **新增文件也算越界**。没授权的改动会被守门直接拒。

### ② 结果需要它吗？

**怎么判**：说出**不做它，哪一条验收标准会失败**。要具体到那一条。

- 能指出具体那一条（例如"验收标准 3：并发下不重复扣款"）⇒ 继续问 ③。
- 只能说"这样更好" / "以后可能用得上" ⇒ **停**。那是过度工程化的标准句式。

### ③ 有证据吗？

**怎么判**：分清你手里的是**证据**还是**猜测**：

| 是证据 | 不是证据 |
|---|---|
| 我实测过，附命令与输出 | "我记得好像会……" |
| 我读过那段代码，第 N 行是这么写的 | "这种写法一般都有问题" |
| 报错原文 / 日志原文 | "一般都会这样报错" |
| 用户原话 | "用户应该是想要……" |

- 是证据 ⇒ 继续问 ④。
- 是猜测 ⇒ **停**。要么去拿证据，要么不做。

### ④ 没它会失败吗？

**怎么判**：假设**不做这件事**，从现在这条路继续走下去 —— 会在哪一步失败？

- 会在**具体某一步**失败（指出那一步）⇒ 做。这就是"必需的改动"。
- 答案是"也不会失败，只是……" ⇒ **停**。这就是过度工程化。

## 四问全过之后

1. 如果它落在**当前授权面之外**：**不要自己动手**。走变更 ——
   `pipeline_clarify_request` 升给需求分析，或让计划 AI 重出计划把范围补进 `change_scope`，
   拿到**新授权**再动。
2. 如果它落在授权面之内：做，并且把**它对应的验收标准**写进交付说明（`dev_to_test` 的
   `acceptance_map`），让测试与审核能对上。
3. 顺手做了却没写进交付说明 ⇒ 审核的前后版本对比会把它当**多改**报出来
   （`pipeline_change_audit` 按基线逐文件比对），那是一次可以避免的往返。

## 一句话

**"不做也不会失败"的事，不做。**
