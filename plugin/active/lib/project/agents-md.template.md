# AGENTS.md · 本项目的协作纪律

> 本文件由流水线在项目建立时生成（项目 `{{PROJECT_ID}}`，首单 `{{TASK_ID}}`，生成于 {{GENERATED_AT}}）。
> ★ 它是**给在本项目里干活的 AI 看的**：动手之前先读完这两条纪律。

<!-- pipeline:section:discipline-commit -->
## 纪律一 · 每次改动之后都要建 commit / 版本

> **每次改动后建 commit / 版本。**

这条没有例外。一次改动做完，就在本项目里留下一个**可回退的版本点**：

- 提交信息写清**这次改了什么**（不要写"update"、"fix"这种看不出内容的）；
- 一次改动一个 commit —— 不要攒着一起提交，否则回退时只能整批回退；
- 没做完的活儿别提交（要么做完，要么明确写成 `wip:` 并说明还差什么）。

★ 为什么这条是纪律而不是建议：没有版本点，就没有"退回去"这个选项。
  出了问题只能靠人回忆改过哪些文件 —— 那时代价远大于随手一次 commit。

<!-- pipeline:section:discipline-test -->
## 纪律二 · 每次改动都要写测试，测试全绿之后才允许交付

> **每次改动写测试、全绿再交付。**

判据是**可执行的**，不是"我觉得测过了"：

- 这次改动要有**对应的测试**（新增功能就新增用例，修缺陷就补一条能复现该缺陷的用例）；
- 交付之前**整套测试跑一遍**，必须是**全绿**（有红就不算交付，不算"基本完成"）；
- 修缺陷时，先让新用例在旧代码上**跑红**，再在新代码上**跑绿** —— 否则无法证明它复现的真是那个缺陷；
- 跑不了 / 没跑的测试，**如实说"没跑"**，不许写"应该能过"。

★ 为什么这条是纪律而不是建议：**没跑过的测试等于没写**，
  而"应该能过"这四个字在真机上从来没兑现过。

## 本项目的版本方式

<!-- pipeline:variant:git -->
本项目**是 git 仓库**：上面两条纪律里的"版本"就是 **commit**。

- 一个项目一个仓库（不是一张单一个仓库）；
- 只在**本地**提交。**未经明确许可不 push、不改远端**。
<!-- pipeline:endvariant -->
<!-- pipeline:variant:snapshot -->
本项目**还不是 git 仓库**：上面两条纪律里的"版本"暂时用**快照目录**代替 commit。

- 每次改动做完，在项目目录下建一个快照目录，名字形如 `b.<年>.<月>.<日>.<段>`；
- 段从 `01` 起，`01…99 → A-01…A-99 → B-01…`（比较按**序数**，不是按字符串）；
- 段到 `Z-99` 就用尽了 —— 那时**改用 git**，不要回绕覆盖旧快照；
- 快照是"没有 git 时的替代品"，不是长期方案：一旦本项目 git 化，
  就把本地快照移除、把最新内容提交进仓库。

★ 为什么不干脆一直用快照：快照没有历史、没有 diff、没有分支 ——
  它只能回答"上一版长什么样"，回答不了"这行是谁为什么改的"。
