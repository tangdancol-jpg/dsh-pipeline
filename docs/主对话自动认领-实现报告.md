### 1.2 判据：**凭什么认定这个会话是某任务的主对话**

只用**主对话自己写下的、跨进程活着的那一条记录**：

```
.pipeline/<任务>/task.json  →  contacts.main
   { role: 'main', agent_id: '<会话 id>', generation, since, previous_agent, why }
```

这条记录由 `lib/store.js` 的 `rememberMainContact()` 落盘，而它挂在 `lib/tools.js` 的**唯一工具出口**（`rememberMainCaller`，`lib/tools.js:363-364`）上 —— 也就是**每一次** pipeline 工具调用之后都会刷新一次。所以它回答的正是需要回答的那个问题：「到上一次为止，**这张单的主对话会话是哪一个**」。

**认定的充要条件（四条同时成立，缺一条就不认）**：

1. `contacts.main` 存在；
2. 它的 `role` 就是 `main`；
3. 它的 `agent_id` 是**非空字符串**（空/缺 ⇒ 这条记录烂了 ⇒ **认领不了**）；
4. 它与**本次调用方的会话 id 逐字相等**（`exec.agent.id`）。

**判据的唯一入口**（纯函数、只读、不写盘、不抛、不改入参）：

```js
// lib/reattach.js:133
export function judgeMainClaim(task, sessionId)
//   → { claim: boolean, reason: <CLAIM_REASONS 里的稳定理由码>, detail, evidence }
```

逐单过一遍的**纯计划**（不动作）：`planMainReattach({ tasks, sessionId, isBound })` —— `lib/reattach.js:215`。

### 1.4 为什么挂在"既有那条缝的最前面"

宿主的执行流水线是 `tools/pre-execute`（`:3225`）→ `ctx.tools.guard`（`:3241`）→ dispatch：

- 挂在**工具出口**太晚 —— 重启后主对话的第一次 `pipeline_transition` 会先被守门以"没有身份"拒掉；
- 挂在**席位作用域判定之后**也轮不到 —— 重启后的主对话**恰好不在令牌表里**，`seatOf()` 会给 `null` ⇒ 直通早退。

★ 但**没有**自己 `ctx.on('tools/pre-execute', …)` 新挂一条缝 —— 因为 `tests/load-smoke.mjs:210-221` 把「`tools/pre-execute` **恰好 1 条**中间件」写成了**既有断言**，而"不许改既有断言/期望值"是硬约束。所以认领搭在**既有那条**缝里调用（`lib/intercept.js:414`），**不改变**它的任何决议（不 deny、不 ask、不改 `next()` 的返回值）。

> 代价（如实写）：`config.intercept !== true` 时它不生效，退化为旧的手动认领 —— 那种配置下**没有任何静默**：`autoReattachMain` 仍可被直接调用，且 `mainReattachEnabled=false` 时装配会打一条 warn。

### 1.7 三条纪律（机械判据，不靠自述）

| 纪律 | 怎么保证 | 实测 |

| **不放宽任何身份校验** | 不碰 `lib/guard.js` 一个字；不碰 `tokens.resolve` / `roleOfAgent` / `bindAgent`。反而**更严**：手动通道 `store.reattach()` 文件头自述"不校验调用方身份"，本机制要求会话 id 与盘上记录**逐字相等** | ✓ 旧令牌照旧无效、守门照旧拒 |

> ★ 为什么留痕**不走** `store.recordAudit()`：那个函数会把行推进 `task.history` 再重写 `task.json`，而 `lib/patrol.js:96-100` 的"最后一次进展时刻"读的正是 `history` 末条 ⇒ 那等于**机制自己制造了进展**（孤儿单那半的注释里对这件事有明文纪律）。所以走只追加的 `audit.jsonl`（与 `store.audit()` / `createChannelAudit` 同一份文件、同一种行格式）。

> ★ 防刷屏：同一条"认领不了"（任务+理由）在进程内只 warn/留痕一次（`refusalMemo`，`lib/reattach.js:285-292`）；但**每次扫的结论里那一条照样在 `refused` 里** —— 不静默与不刷屏是两件事，两个都要。

> ★ 附带的一处**收紧**（如实写）：重启后主对话原本因为"没有令牌"而被拦截缝当作**非管线会话直通**（守门对它的规则一条都不生效，比如"主对话不读代码"）。自动认领之后它被正确认成 `main` ⇒ 那些规则**开始生效**。这是把口子关小，不是开大。

### 3.3 最小改法建议（**未改，需单独授权**）

> ⚠️ **本条牵动投递通道，影响面大 —— 只登记，不动手。**

1. **（已自动解决，但要复验）接线本身**：现文件 `index.js:331` 已有 `ledger: wakeLedger`、`lib/wakeup.js:1486` 已有 `ledger.record(...)`；当前进程（23:27:23 起）载入的是**修好之后**的版本。⇒ **下一次真实投递成功时，账本应当增长一行**。这是复验点，不是改动点。
2. **（建议的最小改法）让"零投递"与"没接线"在盘上分得开** —— 这正是本次误判的形状。现在 `no-main-session` 这类早退走的是 `skip()`（`lib/wakeup.js:1175`），**只写 `audit.jsonl`、不碰账本**，于是"账本一行不涨"同时对应三种完全不同的原因（没触发 / 没接线 / 触发了但全被早退）。最小改法二选一：
   - **甲（改动最小）**：给 `createWaker` 加一个只读、只追加的**心跳行**（例如每次 `wake()` 入口记一条 `{t:'wake-attempt', reason}`），让"唤醒路径跑过没有"在账本上直接可见；
   - **乙（更省盘）**：把 `skip()` 的早退理由也 `noteUnresolved` 一次（带 `reason: 'no-main-session'`），复用既有巡检那条 `unresolved-wake` 播报，不新增行类型。
   - ★ 两条都要先解决**刷屏与有界性**（现有 `noteFailure` 有 60s 节流、`unresolved` 有 500 行上限，甲/乙必须套用同一套上限）。
3. **不要**为了"让账本好看"改成"失败也 `record`" —— `lib/wakeup.js:1430-1434` 的注释写死了"失败**不记账** ⇒ 下一次同类事件照投"，那是有意为之的补发语义，动了会让投不出去的交付被永久判死。
