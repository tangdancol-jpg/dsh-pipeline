〇、一句话读法 + 落盘约定#

三行说清"东西放哪"：

  1. 每一步的产出 = 一份"交接物" ⇒ .pipeline\<单号>\handoffs\NNN-<kind>.json（NNN 是序号）。这是唯一的交付入口（pipeline_handoff，lib/tools.js:2308）。
  2. 席位写的叙述性记录 ⇒ .pipeline\<单号>\records\<role>.md（pipeline_record_submit，lib/tools.js:3453）；留档位汇总 ⇒ requirement.md（pipeline_compile_requirement，lib/tools.js:3507）。
  3. 代码/补丁制品 ⇒ .pipeline\<单号>\artifacts\vN\（pipeline_artifact，lib/tools.js:3311，带版本号）；发生过的每一件事 ⇒ .pipeline\<单号>\audit.jsonl（只追加，一行一个 action）。

「提交」在代码里对应什么：

pipeline_handoff { task_id, kind, payload, role_token } —— 一份结构化交接物。落盘之后，程序会再发一个状态事件把任务推走（例如 dev_to_submitted）。两件事分开做、都要做：交接物落盘 ≠ 状态推进。

「打回」在代码里对应什么：

打回 = 一份"方向相反"的交接物 + 一个回退状态事件。例：测试打回编写 = 交一份 test_to_dev 交接物（lib/handoff.js 的 HANDOFF_SCHEMAS.test_to_dev）并且发 pipeline_transition { event: "test_failed" }。代码里没有一个叫"打回"的独立东西 —— 打回是两种既有动作的组合。 另外有一个把两者打包的工具：pipeline_rework { task_id, target, reason }（lib/tools.js:2748，target 只能 writer / tester）。

一、★ 全部交接物类型总表#

实读来源：lib/handoff.js 的 HANDOFF_SCHEMAS（25 种，本次用 node 直接 import 打印）；方向另在同一份 schema 的 from / to 字段，且与 lib/guard.js:525-563 的 HANDOFF_DIRECTION 逐字重复一份（代码注释自己写着「必须逐字一致 —— 自测里有一条专门比对它们」，lib/guard.js:538-539）。

读表要点

  • 「谁产出」以 HANDOFF_DIRECTION（守门层，dispatch 之前就拦）为准 —— 它对不上会直接返回「角色越权被拦下（交接物方向）」（lib/guard.js:653-686）。
  • 「版本绑定」：payload.artifact_version 是不是必填、以及站点闸会不会拿它做绑定。
  • 「必带证据」：station_confirm 有强制的 basis_refs + basis_digest（lib/handoff.js:613-655 的 validateStationConfirm）。

    • 报出看得见的失败 —— 失败原文照原样拼进工具返回的 summary，并给等价可达路径；

    • 升级叫醒 —— wake:escalated（未被消费的投递不得永久静默）；巡检那条 patrol:unconsumed 也会把它广播出来。
