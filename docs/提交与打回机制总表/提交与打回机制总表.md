## 〇、一句话读法 + 落盘约定

**三行说清"东西放哪"**：

1. **每一步的产出 = 一份"交接物"** ⇒ `.pipeline\<单号>\handoffs\NNN-<kind>.json`（`NNN` 是序号）。这是**唯一**的交付入口（`pipeline_handoff`，`lib/tools.js:2308`）。
2. **席位写的叙述性记录** ⇒ `.pipeline\<单号>\records\<role>.md`（`pipeline_record_submit`，`lib/tools.js:3453`）；**留档位汇总** ⇒ `requirement.md`（`pipeline_compile_requirement`，`lib/tools.js:3507`）。
3. **代码/补丁制品** ⇒ `.pipeline\<单号>\artifacts\vN\`（`pipeline_artifact`，`lib/tools.js:3311`，**带版本号**）；**发生过的每一件事** ⇒ `.pipeline\<单号>\audit.jsonl`（只追加，一行一个 action）。

**「提交」在代码里对应什么**：
> **`pipeline_handoff { task_id, kind, payload, role_token }`** —— 一份**结构化交接物**。落盘之后，程序会**再发一个状态事件**把任务推走（例如 `dev_to_submitted`）。**两件事分开做、都要做**：交接物落盘 ≠ 状态推进。

**「打回」在代码里对应什么**：
> **打回 = 一份"方向相反"的交接物 + 一个回退状态事件**。例：测试打回编写 = 交一份 `test_to_dev` 交接物（`lib/handoff.js` 的 `HANDOFF_SCHEMAS.test_to_dev`）**并且**发 `pipeline_transition { event: "test_failed" }`。代码里**没有**一个叫"打回"的独立东西 —— 打回是**两种既有动作的组合**。
> 另外有一个**把两者打包**的工具：`pipeline_rework { task_id, target, reason }`（`lib/tools.js:2748`，`target` 只能 `writer` / `tester`）。

## 一、★ 全部交接物类型总表

**实读来源**：`lib/handoff.js` 的 `HANDOFF_SCHEMAS`（**25 种**，本次用 node 直接 import 打印）；方向另在同一份 schema 的 `from` / `to` 字段，且与 `lib/guard.js:525-563` 的 `HANDOFF_DIRECTION` **逐字重复一份**（代码注释自己写着「**必须逐字一致** —— 自测里有一条专门比对它们」，`lib/guard.js:538-539`）。

> **读表要点**
> * **「谁产出」以 `HANDOFF_DIRECTION`（守门层，`dispatch` **之前**就拦）为准** —— 它对不上会直接返回「角色越权被拦下（交接物方向）」（`lib/guard.js:653-686`）。
> * **「版本绑定」**：`payload.artifact_version` 是不是必填、以及站点闸会不会拿它做绑定。
> * **「必带证据」**：`station_confirm` 有强制的 `basis_refs` + `basis_digest`（`lib/handoff.js:613-655` 的 `validateStationConfirm`）。

### 1.5 ★ 三处必须知道的"表里写得出、实际交不出去"

**（a）今晚新增的三种**：`station_confirm` / `prebrief` / `diagram_rework` —— 位置在 `HANDOFF_SCHEMAS` 里，方向在 `lib/guard.js:542-546`（代码把这三条单独圈出来注释「★★ T-20261011-56a37e（主管枢纽）：三个新类型的**方向**」）。它们的 `roles.js` 白名单同步放行：`supervisor` 的 `handoffKinds` 含 `station_confirm` / `diagram_rework`，`orchestrator` 含 `station_confirm`，`planner` 含 `prebrief`。

**（b）`roles.js` 的 `handoffKinds` 与 `HANDOFF_SCHEMAS[kind].from` 有 4 处对不上**（本次用 node 逐角色交叉比对，**这是我自己跑出来的，不是抄的**）：

| 角色 | 它声明能产 | 而 schema/守门说只能由谁产 | 后果 |
|---|---|---|---|
| `planner` | `clarification_reply` | `from: ['orchestrator']`（`lib/guard.js:551`） | **交不出去**（守门层「交接物方向」拒） |
| `supervisor` | `human_request` | `human_request.from` 里**没有 supervisor**（`lib/guard.js:561`） | **交不出去** |
| `supervisor` | `clarification_reply` | `from: ['orchestrator']` | **交不出去** |
| `supervisor` | `seat_handover` | `seat_handover.from`（`lib/guard.js:562`）里**没有 supervisor** | **交不出去** |
| `diagrammer` | `human_request` | `human_request.from` 里**没有 diagrammer** | **交不出去** |
| `archivist` | `human_request` / `clarification_request` / `seat_handover` | 三者的 `from` 里**都没有 archivist** | **三类全交不出去** |

⇒ **净效果**：`supervisor` 声明 5 类、**实交得出 2 类**（`station_confirm` / `diagram_rework`）；`archivist` 声明 3 类、**实交 0 类**；`diagrammer` 声明 4 类、**实交 3 类**。

**（c）`supervisor` 的"状态事件能发、交接物交不出"** —— 这是同一族里最尖的一处：
* `lib/states.js:191` 的 `ROLES_CAN_RAISE_HUMAN` **含 `supervisor`**（`by` 名单过关 ⇒ `human_request` 这个**状态事件**它能发）；
* 但 `human_request` 这份**交接物**的方向表不含它 ⇒ 提交时先在守门层被拦。
* ⇒ **状态机说"可以"，守门说"不行"**，而交接物是状态的**前置**（`human_request_blocking` 会拒"没有交接物"的推进，`lib/store.js:2685-2697`）⇒ **主管实际上开不了人工介入**。

**（d）`ROLES_CAN_RAISE_HUMAN` 缺 `diagrammer` / `archivist`**：名单是 `["orchestrator","planner","supervisor","architect","security","writer","tester","reviewer","release","docs","performance","arbiter","human"]` —— **没有 `diagrammer`、没有 `archivist`**，而 `roles.js` 给这两个角色都登记了 `human_request`。

### ★★「否掉」和「打回」**不是同一件事**（代码里是两回事）

| | **打回（rework）** | **否掉（站点不确认）** |
|---|---|---|
| 代码里是什么 | 一条**状态回退边** + 一份方向相反的交接物 | **什么都不发生** —— 只是"该站的 `station_confirm` 没交/不是 `ok`" |
| 谁发起 | `tester` / `reviewer` / `supervisor`（各自 `by` 名单） | 确认方**不作为**（不交那份 `station_confirm`） |
| 状态会变吗 | **会**（→ `returned_to_dev` / `returned_to_test` / `arch_drawing`） | **不会**（停在原地） |
| 有预算吗 | **有**（`rework_budget`，默认 2；架构图 1） | **没有** |
| 后果 | 可预期、可计数、超限有出路 | **卡住**，只能靠 `block` / `cancel` 这两条通配边逃离（见 §五） |

★ **`station_confirm` 的 `decision` 字段只有 `'ok'` 会被当真**：`hubValidConfirms` 用 `h.payload?.decision !== 'ok'` 直接跳过（`lib/store.js:1164`）。而**唯一能产出 `station_confirm` 的工具**（`pipeline_supervise action=confirm_station`）**把 `decision` 硬编码成 `'ok'`**（`lib/tools.js:2672`）⇒ **通过工具**交不出"否掉"。理论上可以走通用 `pipeline_handoff` 手写 `decision:'ng'`（`validateStationConfirm` **不校验**这个字段的取值），但**没有任何状态事件消化它**。

### 3.3 终态与可取消范围

* **终态 2 个**：`closed`（已关闭）、`cancelled`（已取消）—— `TERMINAL_STATES`，出边 0 条。
* **等待态 2 个**：`awaiting_clarification`、`awaiting_human` —— `WAITING_STATES`，出边各 1 条（回到 `(previous)`）。
* **可取消范围**：`cancel` 挂在 `*` 上，注释原文「**任意非终态可取消**」（`lib/states.js:429`）；`block` 同（`:427`）。

## 六、特殊通道

### 6.1 澄清梯（第一级：让需求分析裁定）

* **谁能问**：`ROLES_CAN_ASK_CLARIFICATION`（`lib/states.js:135`）= `["architect","security","writer","tester","reviewer","release","docs","performance","arbiter","diagrammer","planner"]` —— **11 个角色**，**不含 `main` / `orchestrator` / `human` / `supervisor` / `archivist`**。
* **谁答**：**只有 `orchestrator`**（`lib/states.js:551` 的 `clarification_reply: ['orchestrator']`）。
* **工具**：`pipeline_clarify_request { task_id, stage, question, context_digest, blocking, urgency }`（`lib/tools.js:3961`）→ `pipeline_clarify_reply { task_id, request_id, verdict, answer, reason }`（`lib/tools.js:4042`）。
* **`blocking` 的区别**（★ 实读判据在守卫里，不在状态机）：
  * `blocking:true` ⇒ 状态推到 `awaiting_clarification`，但 guard `clarification_blocking` 会**先检查"最近一份 `clarification_request` 的 `blocking` 是不是 true"**，不是就拒（`NOT_BLOCKING`，`lib/store.js:2465-2467`）。
  * `blocking:false` ⇒ **不推状态**（问完继续干活，答复在账本里等它）。此时若有人硬发 `clarification_request` 事件，会被上面那条拒。
* **答复后**：`clarification_reply` → **`(previous)`** —— 回到被打断前的状态（guard `clarification_reply_ok` 要求这条请求必须 `status === 'answered'`，`lib/store.js:2470-2483`）。
* **裁定有两种**：`verdict = "answered"`（给结论）或 `"cannot_answer"`（**升级理由**）—— 后者是通往第二级人工介入的入口。

### 6.4 唤醒与投递：一次交付之后谁会收到通知

* **机制 → 主对话**：交付落盘后，`wakeup.js` 把"席位交付 / 状态推进 / 席位失联"变成一条面向正确收件人的消息，经宿主消息通道注入**下一轮上下文**（是 runtime-context，**不是用户消息**）。
* **机制 → 发起席**（席位侧反向投递）：澄清裁定 / 人工答复落地后，`wakeResumedSeat` 去叫那个"停手等答复"的席位（`lib/tools.js:4408-4414`）；留痕 `seat:wake-delivered` / `seat:wake-failed`。
* **幂等键** = 任务 + 事件类别 + 执行者 + **稳定交付身份**；取不到稳定身份时**不播报**（留痕 `wake:skipped`），**绝不用递增计数器代替**。
* **"叫不醒"时会怎样**（三条，都在代码里）：
  1. **报出看得见的失败** —— 失败原文照原样拼进工具返回的 `summary`，并给等价可达路径；
  2. **不静默降级** —— 例如预登记投不出去时，返回里直接写「等价可达路径是主对话用 `pipeline_dispatch { notify_only: true, role: "tester", message: … }` 手动转达」（`lib/tools.js:2439-2440`）；
  3. **升级叫醒** —— `wake:escalated`（未被消费的投递不得永久静默）；巡检那条 `patrol:unconsumed` 也会把它广播出来。
