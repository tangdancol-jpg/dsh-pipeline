## 一、这套东西是什么

**一句话**：`dsh-pipeline` 是一套「多 AI 协同流水线」插件 —— 它让一张真实的开发单
从"接需求"一路走到"关单"，**每一个环节交给一个不同角色的真实会话去做**，
而每一步能不能往下走，**不靠自然语言提醒，靠代码层的判据**。

### 1.1 它解决的问题（为什么需要它）

插件自己的第一性目标写在 `lib/roles.js:13-19`：

> 「分开跑项目的目的是让 ai 别过度工程化，要求只干自己该干的，编程别跑测试，编排别看代码」

过工程化在实践里长这样（`lib/roles.js:18-19`）：写实现的人顺手把测试也写了（于是测试证明的是他自己）、
做需求与计划的人读了实现（于是开始定字段名、选算法库、加抽象层）。

### 1.2 「靠代码层判据」是什么意思

`lib/boundaries.js:5` 把用户原话作为本项目的目标函数：

> 「**ai 的行为不要靠自然语言限制，要靠代码层直接拦截**」

这句话落地成 `lib/boundaries.js` 里的 `RULES` 表：每条规则都指向**代码里的那个函数**，
而不是指向一段说明（`lib/boundaries.js:64-70`）。例如：

| 规则 | 内容 | 判据落在哪（`lib/boundaries.js` 原文） |
|---|---|---|
| R1 | 编写不跑测试 | `guard:scanTestRunnerCommand`（`:75`） |
| R2 | 控制角色不看代码 | `guard:NO_CODE_READ_ROLES`（`:84`） |
| R3 | 最小改动：改动面必须与授权面相等 | `guard:owningChangeScopeEntry + store:checkManifestAgainstScope`（`:95`） |
| R4 | 职责自限：只干什么，不要多干 | `handoff:validateRoleScope + scanRequirementAnalysisForAllocation + store:ROLE_BOUNDARIES_INCOMPLETE`（`:102`） |
| R6 | 审核只读 + 前后版本对比 | `guard:writeClassOf(own-log) + store:changeAudit`（`:121`） |
| R7 | 没有写权限的位置一律只读 | `guard:writeClassOf + checkOwnPath`（`:129`） |
| R8 | 在册角色必须交出它那一份 | `store:role_products_delivered + diagram_delivered`（`:140`） |
| R9 | 主管枢纽：发起 / 待机 / 唤醒 / 架构图前置 | `states:TRANSITIONS + guard:PIPELINE_TOOL_ROLES.pipeline_supervise` + store 三道（`:151-154`） |
| R10 | 五道确认站点（③④ 必须双确认） | `handoff:HANDOFF_SCHEMAS.station_confirm + store:hub_station_*`（`:168-170`） |
| R11 | 测试提前知情，但不许看产物、不许提前开工 | `handoff:validatePrebrief + store:hub_prebrief_before_write + guard`（`:183-184`） |

**同时它也诚实地列出"判据化不了"的**（`lib/boundaries.js:195-248` 的 `ADVISORY_LIMITS`，C1–C8）。
例如 C6（`:231-234`）：

> 「不得用 shell 的刻意混淆绕过判据（变量拼接 / 编码后执行 / 先写脚本再跑）」
> 「判据化不了：**shell 侧本来就是字符串匹配的 best-effort**」

这一条非常重要 —— 第四章会专门讲**守门的能力边界**。

## 二、角色与三权分立

### 2.1 有哪些角色（实读 `lib/roles.js`）

角色 id 的唯一出处是 `lib/roles.js:30-87` 的 `ROLE` 常量，共 **17 个**：

| 角色 id | 中文 | 类别 `kind` | 写权限 `writes` | 说明（`lib/roles.js` 行号） |
|---|---|---|---|---|
| `main` | 主对话 | control | `readonly` | `:113-123` 接需求/开单/派活/催办/关单；不读代码、不写代码、不做技术判断 |
| `orchestrator` | 需求分析 | control | `readonly` | `:124-144` 出任务卡＋「需求不清楚处」清单；**不分配 AI**；不看代码 |
| `planner` | 计划 | control | `readonly` | `:145-164` 出计划→自检→分配 AI；**不看代码** |
| `supervisor` | 主管 | control | `readonly` | `:165-212` 枢纽位：发起 + 五道确认里主管那一侧；真只读 |
| `architect` | 架构/技术方案 | advisory | `own-dir` | `:213-223` 给模块划分、接口契约、技术选型与风险 |
| `security` | 安全/合规审计 | advisory | `own-dir` | `:224-234` 按基线审计，可独立打回编写 |
| `writer` | 编写 | execution | `workdir` | `:235-258` 按任务卡写代码，**直接提交测试** |
| `tester` | 测试 | execution | `own-dir` | `:259-272` 独立设计用例并执行；**不得替编写改代码** |
| `reviewer` | 审核 | execution | **`own-log`** | `:273-304` 只读比对；**除自己的日志外哪都不能写** |
| `archivist` | 留档 | execution | `own-dir` | `:317-330` 需求档的**唯一写者** |
| `diagrammer` | 架构图 | execution | `own-dir` | `:331-346` 两个站点：前置设计图 + 交付图 |
| `release` | 发布/运维 | execution | `own-dir` | `:347-357` 上线步骤、回滚方案、灰度与监控 |
| `docs` | 文档 | advisory | `own-dir` | `:358-368` 用户文档/变更日志 |
| `performance` | 性能/压测 | advisory | `own-dir` | `:369-379` 基准、压测结果与回归结论 |
| `arbiter` | 仲裁/争议解决 | advisory | `own-dir` | `:380-390` 打回次数用尽时给出有约束力的裁定 |
| `human` | 人工 | control | `workdir` | `:391-401` 异常出口：阻塞、取消、人工放行、回滚 |

**基线四角色**（`lib/roles.js:411`）：`BASE_ROLES = [main, writer, tester, reviewer]` —— 这是
「最少 4 个独立对话」那条硬性要求的落地。

**三权分立的三个执行角色**（`lib/roles.js:416`）：`SEPARATION_ROLES = [writer, tester, reviewer]`，
任何一档配置都必须同时包含这三个。

### 2.2 每个角色"只做什么、不做什么" —— 边界卡机制

角色定义里有三张**能力边界表**，它们不是散文，而是被别处读取的数据：

**(a) `writes`（能写哪里）** —— 取值与守门的映射逐字对齐（`lib/guard.js:133-141`）：

```js
export function writeClassOf(role) {
  const r = String(role ?? '')
  if (READONLY_ROLES.includes(r)) return 'readonly'      // guard.js:135
  if (NO_WRITE_ROLES.includes(r)) return 'none'          // guard.js:136
  if (OWN_LOG_ROLES.includes(r)) return 'own-log'        // guard.js:137
  if (OWN_DIR_ROLES.includes(r)) return 'own-dir'        // guard.js:138
  if (r === 'writer' || r === 'human') return 'workdir'  // guard.js:139
  return null                                            // guard.js:140
}
```

对应四张名单（`lib/guard.js:99` / `:114` / `:115` / `:116`）：

* `READONLY_ROLES = ['main', 'orchestrator', 'planner']`
* `NO_WRITE_ROLES = ['supervisor']` —— ★ 单独一档，理由写在 `lib/guard.js:100-113`：
  主管的 `writes` 写的是 `readonly`，而守门原来认不出 ⇒ **"文档说只读、代码里却能写"**。
  于是给它一个**显式**类别 `'none'`（`:111`），守门按"一字节都不许写"执法。
* `OWN_LOG_ROLES = ['reviewer']` —— 只有自己的日志可写（`OWN_LOG_EXTS = ['log','jsonl']`，`:121`）
* `OWN_DIR_ROLES = ['tester','architect','security','archivist','diagrammer','release','docs','performance','arbiter']`
  （`OWN_DIR_EXTS = ['log','jsonl','md','json','txt']`，`:119`）

**(b) `handoffKinds`（有权产出哪种交接物）** —— 这是"编写不能直接把产物交给审核"的落地处：
`writer` 的白名单里没有 `test_to_review` / `review_verdict` / `test_to_dev`（`lib/roles.js:244`）。
执法在 `lib/roles.js:507-511` 的 `canProduceHandoff()`，调用点 `lib/store.js:3575-3592`，
拒绝原文在 `lib/store.js:3580-3583`：

> 「角色越权：交接物「…」只能由 … 产出，当前调用方是「…」。」
> 「★ 编写角色不能直接提交审核。编写完成后只能产出 dev_to_test（提交测试），由测试通过后再交审核。」

**(c) `canRework` / `canRequestRosterChange`（能不能打回 / 能不能申请改名单）** ——
`supervisor` 两条都是 `false`（`lib/roles.js:200-202`），理由写在注释里："它不打回"、"它不能自己改角色清单"。

**(d) 边界卡（role_boundaries）** —— 由计划 AI 产出、随名单下发：
`lib/tools.js:2884` 的 `role_boundaries` 返回 `[{ role, only, not }]`。
`planner` 的产物里 `validateRoleBoundaries` 是必过的（`lib/handoff.js:253`，调用点 `:1476-1479`）。

### 2.3 三权分立到底分立的是什么

**分立的是"写 / 判 / 核"三种能力，落成三条可机械复核的判据**：

| 分立项 | 判据落在哪 | 拒绝时说什么 |
|---|---|---|
| **编写不判通过** | ① `writer` 的 `handoffKinds` 里没有 `review_verdict`（`lib/roles.js:244`）；② 状态机上**不存在** `developing → ready_review` 这条边（`lib/states.js:372-378` 只有 `dev_submitted → ready_test`） | `lib/tools.js:2319`：「★ 编写不能直接提交审核 —— kind=review_verdict 只允许审核角色产出，状态机也不接受 开发中→待审核。」 |
| **测试不改代码** | `tester` 的 `writes = 'own-dir'`（`lib/roles.js:264`）+ `writeClassOf` 返回 `own-dir`（`lib/guard.js:138`）+ `checkOwnPath`（`lib/guard.js:161-185`） | 写入被判为越权（`lib/guard.js:785-798` 分支） |
| **审核不改代码** | `reviewer` 的 `writes = 'own-log'`（`lib/roles.js:295`），**只允许** `<任务>/reports/reviewer/<role>[-后缀].log|jsonl` | 同上（更严一档） |
| **控制角色不看代码** | `NO_CODE_READ_ROLES = ['main','orchestrator','planner','supervisor']`（`lib/guard.js:335-347`）；三处执法：文件读 `:1033-1055`、检索工具 `:1066-1091`、shell 读 `:1266-1292` | 「主对话不得通过 shell 读取项目代码」之类 |
| **主对话不干活** | `main` 的 `handoffKinds = []`（`lib/roles.js:119`） | `lib/store.js:3590`：「★ 主对话不产出技术交接物 —— 它只负责派活、路由与关单。」 |

★ **为什么审核的权限是"只读"而不是"不许写源码"**（这是**收紧**，理由写在 `lib/roles.js:286-293`）：

> 「审核一旦手里有"写"的权限，就有"顺手改一下"的诱惑 —— 而审核的角色意义恰恰是**独立核对**。
> 给它一支笔，它就从"核对者"滑向"共谋者"：发现了问题顺手改掉，然后判自己 OK。收掉这支笔，它就只能**报出来**。」

### 2.4 席位（seat）：同一个角色可以有多个实例

`lib/roles.js:418-441`：

* `MAX_WRITER_SEATS = 6`（`:441`，本轮由 3 提到 6）
* 席位 id 形如 `writer#1`，**不是角色 id**（`lib/roles.js:429-430`）
* 席位 id 的合法形状：`SEAT_PATTERN = /^writer#[1-9]\d*$/`（`lib/roles.js:480`）
* **`count === layers.length`** 是一条不变量（`:438-439`）：一个层就是一个席位
* `count = 1` 必须是**同一套机制的退化情形**（`:425-428`）：那时 `partitions` 只有一条，`scope_paths: ['.']`

★ 一个反复咬人的坑：**席位键的口径**。席位 id **本身已经是全限定的**（`writer#3`），
所以正确的键拼法是 `seat || role`，**不是** `${role}#${seat}`。后者会造出 `writer#writer#1`。
这条口径在三个地方被写死为"必须一致"：`lib/liveness.js:313-325`、`lib/wakeup.js:280-284`、
`lib/store.js:3555`（后者被 `lib/liveness.js:313` 直接点名）。
`lib/wakeup.js:281-283` 记下了现场：账本里 20+ 条 `wake:delivered` 全是双前缀，**导致唤醒正文里的"谁"与账本里的席位对不上**。

### 3.5 `unblock` 的恢复点：一条被真单打出来的规则

`block` 是 `{ from:'*' }`，所以对同一张单连按两次 `block`，第二次的 `from` 已经是 `blocked`。
旧判据只问"`from` 是不是等待态"，对 `blocked` 照样成立 ⇒ **恢复点被覆盖成 `blocked` 自己**
⇒ 之后 `unblock` 回退到 `blocked`，变成**空操作**（`lib/states.js:570-578` 记的就是真单
`T-20261011-5a871c` 的现场）。

修法（`lib/states.js:555-564` 的 `isUsableRecoveryPoint`）：恢复点必须**五条同时成立**——
非空串、是已知状态、**不是 `blocked`**、不是终态、不是等待态。
不可用就按任务进度**回落**（`lib/states.js:595-634`）：开过工 ⇒ `developing`；否则 ⇒ `ready_dev`。
两个落点都是非终态，**永远不返回 `cancelled` / `closed`**（`:588-589`）。

`store.transition` 里的两处收紧（`lib/store.js:1650-1667`）：① 已是阻塞态时**不覆盖**恢复点；
② `unblock` 时若恢复点不可用，**就地修好账本**（把合法落点写回去），免得下次再回落一遍。

#### ★★ 今晚刚落地的「机器产物豁免」

**现场**（`lib/hashgate.js:63-71`）：

#### ★★ 硬栏杆（为什么这不放松闸门）

代码里给了**两条可机械复核的论证**（`lib/hashgate.js:81-88`）：

1. **越界那一支一个字节没动**（`:82-83`）：`unauthorized` 仍由 `changeAudit` 按授权面算，
   机器产物只要落在授权面之外，照样进 `unauthorized` ⇒ 照样 `pass=false`。
2. **豁免只对"没被判越界"的路径生效**（`:84-88`）：实现就是 `:201-205` 的 `unauthorizedKeys` 集合 +
   `:210` 的条件 `!unauthorizedKeys.has(key)`。原文推论：

   > 「于是"豁免"在数学上不可能掩盖任何一处越界改动。推论：豁免影响到的只可能是"**本来就在授权面内**"的机器产物。」

**残余风险也如实写了**（`lib/hashgate.js:90-94`）：

> 「如果某张单把 `tests/` 授权给了编写席，而编写把一处真实改动**故意命名**成 `tests/<随便什么>-last-run.txt`，它会落进豁免。这是选项 A 的已知代价。」

**豁免不静默**（`:96-97`）：被豁免的路径逐条进 `verdict.ignored_machine_artifacts` 与
`counts.machine_artifacts`（`:244-245`、`:251-252`），并进 store 的 `hash_gate_checks` / `gate:hash` 审计行。

#### 连续不过的计数与自动交人工

### 5.3 唤醒投递：主对话是怎么被叫醒的

**为什么需要它**（`lib/wakeup.js:10-21`）：旧的**子代理**通道自带回调（子会话结束，
harness 会往协调者注入一条 `Background subagent … finished`）。新的**真实会话**通道只做了三步
（建会话 / 投派活单 / 读回会话头），**没有第四步「交付回调」**，于是席位交付时主对话完全不知情。

**两条硬判据**（`lib/wakeup.js:26-42`）：

1. **消息必须带 `source`，而且是 `runtime-context`**。
   缺 `source` ⇒ 宿主会无守卫地读 `message.source.kind` ⇒ `TypeError` ⇒ **整个 turn 以 error 收尾**
   （`:28-30` 记的就是 2026-10-11 那次事故：子会话 `turn/start` 之后 **277 ms** 静默死亡）。
   所以消息**一律**走 `lib/hostmsg.js` 的 `hostMessage`（唯一出口）。`kind` 取 `runtime-context`。
2. **只能发给主对话，而且同一次交付只注入一次**。目标会话**只**从
   `createMainSessionRegistry` 登记的那一份取，**从不**接受调用方传入的 sessionId
   ⇒ 结构上就不可能投错会话（`:36-38`）。

**触发表** `WAKE_TRIGGER_TOOLS`（`lib/wakeup.js:138-172`）：7 类 ——
`handoff` / `artifact` / `record` / `clarify` / `human` / `transition`（`advancesState:true`）/ `liveness`。

**投递两条路**（`lib/wakeup.js:989-1048` 的 `deliverWake`）：

* **首选** `(a)` `agents.get(sessionId).followup(message)` —— source 保住（`:1013-1015`）
* **退路** `(b)` `sessionController.prompt({requestId, sessionId, mode:'queue', content})` ——
  ★ **宿主会把 source 改写为 `kind:'user'`**，所以返回 `sourcePreserved:false`（`:1030-1044`）；
  而且"这次到底新入队还是被 requestId 幂等挡下"**宿主不告诉调用方** ⇒ 那一栏只能是 `null`（**不可知**），
  写 `false` 就是假装知道（`:1034-1039`）。

#### 吞法 1 · 静默 `no-stable-identity`（拿不到稳定交付身份时**直接不叫**）

* **现场**：`lib/wakeup.js:417-423`。真单 `T-20261012-8cdee0` 的 `audit.jsonl` 第 8 行（我实读）：

  ② `warn` 出声（`:1322-1325`）；
  ③ **记进账本的 unresolved 列表**（`:1318`），由**巡检**再叫一次。
  原文（`:1304-1305`）：「**静默跳过被彻底取消：跳过也要有人知道。**」

#### 吞法 2 · 去重吞掉**不同**的消息

* **现场**（`lib/wakeup.js:106-111`）：一条「任务被冻结」的唤醒**从未送达**主对话，
  而审计里**什么都没有** —— 既不是 `delivered` 也不是 `skipped`：它是被"去重"吃掉的。
* **修法**：**去重这一支必须自己说出来**。
  * 新增审计动作 `WAKE_AUDIT.dedup = 'wake:dedup'`（`lib/wakeup.js:112`）
  * 内存表命中 ⇒ 记 `wake:dedup`（via `memory`，`:1348-1358`）
  * 账本命中 ⇒ 记 `wake:dedup`（via `ledger`，`:1367-1379`）
  * 重放路径 ⇒ 记 `wake:dedup`（via `ledger-replay`，`:1278-1297`）
* ★ **同一处还修了一个更狠的**（`lib/wakeup.js:1421-1448`）：
  旧代码在投递**失败**时也 `delivered.set(key, {ok:false,…})`，而幂等门只看 `delivered.has(key)`
  ⇒ **一次投递失败会把那个交付键永久判死**，一次都不补发，审计里连"跳过"都不留。
  改法：**失败不记账**（`:1450-1451` 只在成功时才 set），下一次同类事件照投。
  代价是失败会重复留痕 + 每次重试都 warn —— 注释 `:1432-1434` 说这是**故意的**：「投不出去必须吵，不能安静。」

#### 吞法 3 · 拿**别人**的交付 id 冒充本次

* **现场**（`lib/wakeup.js:417-420`）：一条「交了一份交接物」的唤醒，键里用的是**编写席**的 id：
  `T-…|handoff|**tester**|H-7d661abef1479500` —— 实体是 writer 交的，键里的执行者写着 tester
  ⇒ **生产者与实体错配**。
* **根因**：`ledgerIdentityOf` 既不管**是谁**交的，也不管**播没播过**。
* **修法**：新增 `ledgerIdentityScoped`（`lib/wakeup.js:584-639`），三条硬判据：
  ① **作者对齐**（`:608-609`）：`if (actor.length > 0 && c.author.length > 0 && c.author !== actor) continue`
  ② **没播过才算新**（`:624-628`）：算出来的键若已在账本里 ⇒ 不当新事件用
  ③ 一条都没有时**不再编造**，而是分清"重放"与"真的还没产生"（`:631-638`）
* ★ 同一处还修了**席位键的双前缀**（`lib/wakeup.js:280-284`）：
  旧写法 `${role}#${seat}` 产出 `writer#writer#3`，实测账本里 20+ 条 `wake:delivered` 全是它
  ⇒ 唤醒正文里的"谁"与账本里的席位对不上（**归因错误**）。

#### 吞法 4 · 延迟重放（同一条事件在已处理完之后再响一次）

* **现场**（`lib/wakeup.js:367-369`）：之所以会重放，是因为旧代码在拿不到判别子时
  **退到"任务历史的长度"** `h<historyLen>` —— 而那是**单调递增的计数器**，
  保证"每次都不同" ⇒ **去重永远不可能命中**（实测 `h228 → h233 → h237`，同一条人工介入请求被播报三遍）。
* **修法**：三层。
  ① **不许退成计数器**（`lib/wakeup.js:1243-1244`：`★★ 绝不退回 h<historyLen> 递增计数器（v1 去掉它的原因，不许改回去）`）
  ② **跨进程的"恰一次"落盘**：`lib/wakeledger.js`（见 5.7）
  ③ **升级事件与"没投出去"的事件分开表达**：重放走去重（记 `wake:dedup`），
  真没有身份走"看得见的失败"（记 unresolved）。
* 另外还有一处**形状级**修法：状态推进的判别子从"数字后缀"改成
  `<from>→<to>@<历史 at>`（`lib/wakeup.js:612-622`）—— 既保留既有断言要的箭头形态，又保证逐次唯一。

#### 吞法 5 · 投错单（同一主对话在 A 单的记录，被报成 B 单的交付）

* **现场**（`lib/tokens.js:337-352`，注释原文）：
  `roleOfAgent` 按 `Map` 插入顺序返回**第一条**命中，而主对话会为**每一张它开过/认领过的单**
  各持一枚 `main` 令牌 ⇒ 两种语义被混成一件事：
  * "这个会话是 `T-A` 的主对话吗" —— 想要的；
  * "这个会话第一个被绑成主对话的是哪张单" —— `roleOfAgent(agentId)` 给的。

  后果**是沉默的**：`contacts.main` 被反复写在**老单**上，**新单一个字节都落不下来**
  ⇒ 新单的交付唤醒全部 `wake:skipped / no-main-session`，而老单看着一切正常。
  （现场：`T-…5a871c` 一直响到它没事件为止，`T-…214043` / `T-…56a37e` 从头到尾一条唤醒都没有。）
* **修法**：新增 `tasksOfAgent(agentId, role)`（`lib/tokens.js:360-369`）——
  判据与 `roleOfAgent` **同源**（同两个字段：`agentId` + `role`），只是**不做取舍**：
  「该由调用方决定要哪一张单，不该由 `Map` 的插入顺序决定。」
* 另一条同族的修法在唤醒侧：目标会话**只**从登记表取（`lib/wakeup.js:36-38`），结构上不可能投错会话。

#### （附）第 6 种 · `no-main-session`（没有主会话可投）

不是"吞"，是**没有目标**。修法（`lib/wakeup.js:1078-1179`）：两道来源、**同一份判据**：

* ① 内存登记表（本进程内主对话调过 pipeline 工具 ⇒ 最热、最准）
* ② **落盘那份**（`task.contacts.main`）—— 补的正是"DSH 重启后、主对话还没再调过任何工具"的那个窗口

原文（`:1153-1155`）：「**没有它，重启后的第一次交付会被静默跳过**，而那恰恰是最常见的场景（用户关掉再打开）。」
两道都没有 ⇒ `skip('no-main-session', ...)` + audit 一行，**绝不抛错把调用方带崩**（`:1173-1179`）。

### 5.8 重启后自动认领 + 重启即失的令牌表

#### 为什么令牌表重启即失，而且这正是想要的语义

`lib/tokens.js:36-43`：

> 「令牌表。**内存态 —— 进程重启即失效，这正是想要的语义**："上一次会话拿过令牌"不构成这一次的通行证。」

#### 但"身份没了"会造成一个死锁

`lib/tools.js:743-751` 写得很清楚：

* 令牌随重启没了（令牌表是进程内存态）；
* `pipeline_bind_role` 救不了它 —— 那个工具**先 `tokens.resolve` 再 `bindAgent`**，
  令牌表空了它必然失败（**死锁**：认领要令牌 → 令牌要主对话 → 主对话要身份）；
* 同一个 `task_id` 又不能重开（`store.js` 的 `TASK_EXISTS`）；
* 而 `pipeline_task_open` 是全插件**唯一不需要身份**的写工具（守门表里它是 `null`）。

⇒ **为什么需要 `pipeline_task_open { reattach: true }`**：它是回到老单的**唯一**入口。
实现：`lib/tools.js:756-799`，落地 `store.reattach(id, { agentId })`（`:771`）+ 铸一枚新 `main` 令牌（`:776`）。
语义纪律（`:753-754`）：「认领 = **保留全部历史**（history / handoffs / artifacts 一条不动），只换身份。」
`task_id` 在 `reattach` 时**必填**（`:757-768`）。

★ **真单实证**：`T-20261012-8cdee0` 的 `audit.jsonl` 第 56 行：

```json
{"at":"2026-10-13T09:50:11Z","task_id":"T-20261012-8cdee0","actor":"main","action":"reattach",
 "agent":"session-…","from_state":"analyzing",
 "note":"★ 重启后重新认领主对话身份（不覆盖任何历史）"}
```

### 6.1 活着证据三件套 + 今晚新增的"会话文件仍在增长"

**入口**：`lib/store.js:1776` `async checkLiveness(taskId, opts = {})`；
**纯判据**：`lib/liveness.js:464` `seatLiveness(task, now, opts)`。
默认静默阈值 `DEFAULT_SEAT_SILENCE_MS = 5 分钟`（`lib/liveness.js:62`）。

**四条判据同时成立才算"失联"**（宁可漏报也不误报）：

| # | 判据 | 代码 |
|---|---|---|
| ① | **超时**：`now - 最后活动 >= silenceMs` | `lib/liveness.js:515` `const timedOut = elapsedMs !== null && elapsedMs >= silenceMs` |
| ② | **轮到场了**：该角色的下一步就该它动 | `lib/liveness.js:296-308` 的 `EXPECTED_ROLES_BY_STATE`；判据 `:502` `expected.includes(role)` |
| ③ | **没有任何活着的证据** | `lib/liveness.js:400-450` 的 `evidenceOfLife` |
| ④ | ★ **会话文件仍在增长**（今晚新增，**优先级最高**） | `lib/liveness.js:505-510` |

**判据 ② 为什么是防误报的关键**（`lib/liveness.js:25-27`）：
「双轨派活下审核是与编写同时开工的，它可能合法地沉默很久（链路是 编写 → 测试 → **才**交审核）。没有这一条，审核每次都会被误判成失联。」
所以 `EXPECTED_ROLES_BY_STATE` 里 `developing` **只列 `writer`**（`:299`）。

**判据 ③"活着证据三件套"的完整清单**（`lib/liveness.js:394`：「顺序按"最硬的证据在前"」）：

| 序 | 证据 | 判据 | 行 |
|---|---|---|---|
| ① | **交接物** | 该角色产出过交接物（且时间晚于派活时刻） | `:411-417` |
| ② | **席位提交表** | `task.writer_submissions[seat]`（按 seat **精确匹配**，多席位不会互相顶替） | `:419-426` |
| ③ | **水位自报** | `task.context_reports[]` 里该角色的上报 | `:428-433` |
| ④ | 历史流水 | `task.history[]` 里 `actor === role` 的动作 | `:435-440` |
| ⑤ | 继任 | `task.successions[]`（换班本身就是处置，老席位不该再催） | `:442-447` |

★ **"水位"是什么**：它是**上下文水位**（该席位自己上报"我的上下文用了百分之多少 + 依据"），
**不是**席位心跳。定义在 `lib/store.js:1487`（`/** ★ 上下文水位上报（席位自报 + 必须给依据）。 */`），
写入入口 `lib/store.js:5547` `async reportContext(input)`，字段 `context_percent` 在 `lib/handoff.js:1178`。

**★ 判据 ④"会话文件仍在增长"——今晚新增的那一条**

**现场**（`lib/liveness.js:67-76`）：席位被判「0 交接物 / 0 流水 / 0 水位自报」⇒ 机制自动把任务推到「已阻塞」；
**同一时段**它的会话日志 `session.v4.jsonl.zstd` 30 秒内从 381,679 B 长到 392,396 B（**+10,717 B**）。
「那一次自动冻结**直接挡掉了一份已经提交的 dev_to_test**。」

**根因**（`:74-77`）：原来那三条判据**全部只看任务台账**，而席位"正在读源码、逐文件算哈希、编译级冒烟"
这类**纯工作**根本不产生台账事件。

**判据本体**：`activityOfSamples(prev, cur, opts)`（`lib/liveness.js:164-228`）。关键概念有三个：

* `known`：**本次拿不到活动证据**（`false`）≠"它没动"（`lib/liveness.js:160`）
* `grew`：两次采样之间涨了 ≥ `DEFAULT_ACTIVITY_MIN_BYTES = 1024` 字节，且间隔 ≤ `DEFAULT_ACTIVITY_MAX_MS = 2 分钟`（`:93`、`:96`）
* `conclusive`（今晚新增，`:161-162`）：`false` = 这次结论**不能单独用来判死**，必须走确认门

两条**单样本**就能判的硬证据（这是今晚修的重点）：

1. **mtime 刚刚被写过**：`lib/liveness.js:179-186`，宽限窗 `DEFAULT_ACTIVITY_FRESH_MS = 60 秒`（`:119`）。
   为什么需要它（`:108-113`）：采样只在"任意角色的下一次工具调用"时发生；
   席位写报告的那几分钟里**没人调工具**，于是上一次采样可能已经是几分钟前 ⇒ 差值窗口用不上。
   取值理由（`:115-117`）：必须**远小于**静默阈值（5 分），否则"死了之后 4 分钟才来看"也会被当成活着
   —— 「那就等于把检测关掉了（用户点名不许）」。
2. **跨窗但确实长了**（`:194-205`）：两次采样相隔超过窗口，但这一段里 `+≥1024` 字节
   ⇒ 「窗口内仍在增长」。

**"不许只凭一次安静就冻结"**：`DEFAULT_SILENCE_CONFIRMATIONS = 2`（`:99`），
判据 `lib/liveness.js:531-535`（`quiet + 1 < confirmations` ⇒ 本轮不冻结，记 `pending`）。
★ 但它**不是"关掉检测"**（`:470-480`）：只在 `opts.gateApplicable === true`
（本任务的活动采样"本来做得到"）时才要求连续确认；否则退回台账三条判据，一次安静即可冻结。

**★ 今晚修的第二个缺陷（P0-3）**（`lib/liveness.js:519-529`）：门条件从 `act.known !== true`
改成 `act.conclusive !== true` —— 旧写法把三种**其实没有实证**的形状（首次采样、两次采样跨窗、时钟回退）
当成"测到了、没长" ⇒ **绕过确认门、一次观察即冻结**。
而 `quiet + 1` 这个计数**在 pending 时也必须落盘**（`:557`），
否则计数器永远回不到 `confirmations` ⇒ 门一旦开着就**永不冻结**（等于把检测静默关掉）。

**★ 采样根目录的候选列表**（`lib/liveness.js:121-151`）：
根因是 `sampleSessionActivity` 原来**只认** `DSH_SESSIONS_DIR` / `DSH_HOME` 两个环境变量，
插件进程里取不到 ⇒ 采样**从来没成功过一次**（实测台账：`liveness.samples` 键从未出现、
6 条 `transition:block` 的 `evidence[].activity.sample_at` 全是 `null`）
⇒ 「会话文件在增长」这条证据**恒等于零**。
修法：`sessionsRootCandidates()`（`:138-151`）按"越具体越先试"排四个候选根，
**每一个都必须真的命中 `<sid>/session.v4.jsonl.zstd` 才认**（`:131-132`）。

★ **本条标「需重启后复验」**：`lib/liveness.js` 的落盘时间是 2026-10-13 23:35，
且上面这条"采样从来没成功过"的诊断是**代码注释里的自述**；我没有重启去验证它现在真的采到了。

这是本插件最贵的一类误判。分三层：

#### （1）**"回合中止"是另一条判词**（`lib/runfail.js`）

**现实里的中止长什么样**（用户现场截图原文，被写进交接档与代码注释）：

```
🔴 本轮运行失败  DeepSeek Messages stream: tool input is invalid JSON  [MALFORMED_RESPONSE]

★ 这一类**在旧版里会被当成"静默"** —— 席位崩了、没人调工具、台账一动不动 ⇒ 判失联并冻结。
现在它有了自己的判词与自己的留档。

#### （2）**"正常闲置"**：等待态与"还没轮到它"

* 等待态（`awaiting_human` / `awaiting_clarification`）**本来就不该有人动** ⇒

  没列到的状态（待分配 / 待计划 / 已通过 / 各等待态 / 已阻塞 / 已取消 / 已关闭）一律**不报失联**
  （`lib/liveness.js:288-295`）。

#### （3）**判词长什么样**（给人看的原文）

失联席位的判词（`lib/liveness.js:660-681`）：

```

★ **一处今晚修好的"说反话"**（`lib/liveness.js:586-593`）：
`describeSilentSeats` 里本来就有"并且**这一次拿不到会话日志**"这一支，但调用方**一直没传**

### 6.3 ★ 送达 ≠ 接管

**现场**（`lib/wakeup.js:1584-1589`）：

> 一条要素俱全的 `delivered` 之后 **18 小时零动作**，而同一条通道在另一类事件上 **23 秒**就产生了动作
> —— 两次投递在台账上的形态字段**完全相同**，差别只在"接管侧有没有痕迹"。
> 所以判据不能只看投递侧，得有这一半：**目标随后确实带着这条投递动了**。

**修法**：账本里加一条 `consumed` 记录，与原事件**用同一个键配对可读**。

| 侧 | 投递留痕 | 接管留痕 | 键的形状 |
|---|---|---|---|
| 主对话 | `wake:delivered`（`lib/wakeup.js:1459`） | `wake:consumed`（`WAKE_AUDIT.consumed`，`:114`） | `<taskId>\|<kind>\|<actor>\|<disc>`（`wakeKeyOf`，`:276-287`） |
| 席位 | `seat:wake-delivered` / `seat:wake-failed`（`lib/tools.js:505`） | `seat:wake-consumed`（`lib/wakeup.js:121`） | `<taskId>\|<kind>\|seat:<role[#seat]>\|<requestId>`（`lib/tools.js:498`） |

**★ 一条重要的收紧**（`lib/tools.js:283-298`）：
「**只认会改状态的那类工具**（`opts.mutating === true`）—— 一次 `pipeline_status` 只读查询**不算**接管」。
（`mutating` 标记在 `lib/tools.js:345-347` 被用于功能开关闸。）

**未接管就会再叫一次**：`escalateUnconsumed`（`lib/wakeup.js:1627-1658`）。
它有三条纪律（`:1617-1626`）：不冒充新事件（类别是 `escalation`）、不复用旧身份
（键是 `<原键>#escalated`，读得出它升的是哪一条）、不把原事件原地重放（原键一个字没动），
且**同一条只升一次**（`markEscalated` 记账）。

### 6.4 ★ 交付不静默丢弃（含 20,000 字符上限）

**口径**（`lib/store.js:2040`）：`★★ **A13：被拒收的交付不许静默消失。**`
原文（`:2042-2044`）：「要么接收，要么拒收但对席位与主对话都可见且内容留档（能查回原文）」。

**落点**：追加进任务数据 `task.rejected_deliveries[]`（`lib/store.js:2060`、`:2099`），
即 `.pipeline/<taskId>/task.json`（`lib/store.js:718`）。

|---|---|

```js
2078:        if (body.length > MAX_REJECTED_PAYLOAD_CHARS) {
2079:          payload = { truncated: true, chars: body.length, head: body.slice(0, MAX_REJECTED_PAYLOAD_CHARS), note: '★ 内容超长，这里只留前一段（完整原文在席位那次调用的返回值里；这条留档的意义是"它交过什么、为什么被拒"可查）。' }

取值理由（`:633-637`）：「任务文件已经 MB 级，单条留档不该成为新的大头；

**审计**：`delivery:rejected` + `archived: true`（`lib/store.js:2100-2107`）。
**触发点**：`lib/tools.js:2368`（`pipeline_handoff` 收到失败结果后），播报文案 `:2387` / `:2405`。

（未命中）。这两类拒收只留在审计与那次调用的返回值里。

也就是说**那一节并不存在**。要查只能直接读 `task.json`。

### 6.5 中止 / 失联 / 无进展 —— 三条判词的分工（汇总表）

| 现象 | 判词来源 | 触发点 | 会不会冻任务 |

## 七、主管枢纽（最新站点）

### 7.1 一条链：从发起面到关单

用户原话（`lib/states.js:214-216`）：

> 「主管发起（需求分析/计划/架构ai）对话 → 需求ai分析同时计划和架构ai待机 → 需求ai分析将结果提交主管
> → 同意后交给架构ai先画架构图 → 架构图完成后给主管确认是否满足要求 → 主管确认后交给计划ai……」

落地形状（`lib/states.js:14-21` 的文件头）：

```
待分配 →（主管发起）需求分析中 →（需求结论交主管）主管受理中
      →（第①道确认＋唤醒点 A）架构位出图中 →（架构图产出）架构图待主管确认
      →（第②道确认＋唤醒点 B）计划位已唤醒待派 →（计划位派活）计划中
      → 待开发 → 开发中 → 待测试 → 测试中 →（第③道双确认）待审核
      → 审核中 → 已通过 →（第④道双确认）已关闭 ⇒ 用户收到结果
```

**两席待机 + 两个唤醒点**（`lib/states.js:228-254`）：

| 唤醒点 | 值 | 唤醒谁 | 组 |
|---|---|---|---|
| A | `need_agree` | `architect`、`diagrammer` | 架构位 |
| B | `diagram_confirm` | `planner` | 计划位 |

★ 为什么 `architect` 与 `diagrammer` 都在唤醒点 A 之下（`lib/states.js:239-243`）：
「roles.js 里这两个角色**不是一回事**（architect 出"该怎么写"的文字方案，diagrammer 出"画成什么样"的图），
而用户要的"架构图"由 diagrammer 产出；架构位这一**组**在唤醒点 A 一起被唤醒……
这不是把两个角色混为一谈，而是把它们**归属到同一个唤醒点**。」

**★ 架构图前置是"表上"的硬序**（`lib/states.js:20`、`:356-357`）：

> 「★ 架构图前置是**表上**的硬序：`analyzing` 没有直达 `planning` 的边。」
> 「★ 这一段的**形状**本身就是判据：从 `analyzing` **不存在**直达 `planning` 的边 ⇒「先出计划、后出架构图」在表上无路可走。」

**发起方只有主管**（`lib/states.js:358-360`）：`by` 名单只含 `supervisor`；
main 代发会被 `applyTransition` 的 `by` 名单直接拒（第一道），
第二道在守门的工具-角色表 `pipeline_supervise: ['supervisor']`（`lib/guard.js:492`）。

### 7.5 ★ 新站点怎么"纳入"既有四类判据（而不是另起一套）

★ **主对话默认拿到的是脱敏摘要**（`:2841`：「补丁正文、失败日志正文、运行命令正文已隐去」），
正文里会明示一句（`:3144-3146`）。
`full=true` **只对执行角色开放**（`:2997-3012`，拒：「`full=true` 只对**执行角色**开放」）。

**做完会发生什么**：它**不改状态**，但**会做失联处置**（`lib/tools.js:3039-3057`）。
理由（`:3041-3045`）："席位秒死、没有角色再调工具，而主对话一定会查状态"——
所以查询时顺带扫一遍失联。

### 8.3 派活：`pipeline_dispatch`

**参数**（`lib/tools.js:1806-1851`）：`task_id` / `role` / `seat` / **四槽**（`permission` `:1822`、`mode` `:1823`、`model` `:1824`、`reasoning` `:1825`）/
`spawn` `:1826` / `reassign` `:1838` / `notify_only` `:1847` / `stop` `:1848` / `message` `:1849` / `note` `:1850` / `role_token` `:1851`。

**什么时候用哪个**：

| 场景 | 怎么填 | 会怎样 |
|---|---|---|
| **普通派活** | `{ task_id, role, ...四槽 }` | 建一个真实会话、钉四槽、读回核对、铸令牌、投派活单（`lib/transport/index.js:896-1042`）；状态推进由你自己调 `pipeline_transition` 完成（派活本身**不改状态**） |
| **多席位** | `seat: "writer#2"` | `seat` 在 `role=writer` 且 `count>1` 时**必填**（`:1808`）。★ 注意席位 id **全限定**，写 `writer#2` |
| **席位失联重派** | `{ task_id, role, seat, reassign: true }` | 任务若在「已阻塞」⇒ **先自动 `unblock` 回到阻塞前的状态**（`:1934-1957`），再派同一席位。★ **不消耗打回预算**（`:1877-1878`） |
| **只传话，不建会话、不改状态** | `{ task_id, role, seat, notify_only: true, note: "要说的话" }` | 从**派活台账**找那个既有会话投一句话（`lib/tools.js:566-572`）。投不出去返回 `ok:false` + 原因 + 等价路径（`:1920-1932`）。★ **`note` 不能为空**（`:1907`） |
| **叫它停手** | 同上 + `stop: true` | 消息开头变成「【流水线 · 主对话指令 · **停手**】立即停止你正在做的事」（`:567-568`）。★ 停不停由席位自己执行 —— 「插件不替它改状态，也不假装它已经停了」（`:1844-1845`） |

**做完会发生什么**：成功 ⇒ 闸门在该角色下次调用守门时按新令牌认人；
派活记录写进 `task.dispatched[]`（跨进程活着，重启后靠它认出席位，见 5.8）。

### 8.4 推状态：`pipeline_transition` —— ★ 先重读，再做

**参数**（`lib/tools.js:2470-2473`）：`task_id`、**`event`**（`:2471` 列了常用值）、`note`、`role_token`。

**★ "先重读再做"到底落在哪一层** —— 这一点必须说清楚，因为它容易误解：

* **工具本体不重读**：`lib/tools.js:2481-2494` 只做 `resolveActor` → `store.transition(...)` → `indexTask(...)`，全函数无重读。
* **重读发生在 store 层**：`lib/store.js:1630-1631` 每次迁移都 `const task = await loadTask(input.taskId)`，
  而 `loadTask`（`:845-873`）会**与盘上指纹对账**：盘比内存新 ⇒ **丢掉内存那份、从盘重载**
  （`:848-850`，「读前对账：内存实例只在"它确实就是盘上那份"时才可信」）。
* **唤醒正文里的那句话是给"人"看的纪律**：`lib/wakeup.js:852-855` 与 `lib/tools.js:4415`：

  > 「★ 上面这一行状态是**快照**（取样于 …）—— 唤醒要排队投递，**动手前请先 `pipeline_status` 重读一次**：状态可能已经变了，照旧状态做会被状态机拒掉。」

  **为什么不做成"投递时重读"**（`lib/wakeup.js:847-848`）：
  「唤醒是投进目标会话的**队列**，投递完还要排队等它那一步，排队期间的漂移照样会发生 ⇒ 单靠重读治不了根。」

**结论（照做）**：收到唤醒后，**先 `pipeline_status` 看当前状态与"下一步合法事件"，再决定推哪个 `event`**。
唤醒正文报的状态**只是取样那一刻的快照**。

**做完会发生什么**：状态按 `TRANSITIONS` 表迁移（合法组合在第三章的表里）；
非法组合会被拒并**列出当前可用事件**（`lib/states.js:496-505` 的 `explainRefusal`）。
返回 `{ ok, from, to, summary }`（`lib/tools.js:2493`）。

### 8.5 答澄清：`pipeline_clarify_reply`

**谁能调**：**只有需求分析**（`lib/guard.js:511` `pipeline_clarify_reply: ['orchestrator']`）。
**前提**：必须真有一条已答复的澄清记录（`lib/store.js:2470-2482`）——
`:2472` 找不到 ⇒ `NO_CLARIFICATION`；`:2475` `status !== 'answered'` ⇒ `MISSING_CLARIFICATION_REPLY`。

**两种裁定**（`lib/handoff.js:1697-1719`）：`answered`（带结论）或 `cannot_answer`（带升级理由，
且**必须** `escalate`）。裁定落地后：状态**回到被打断前的那个状态**（`lib/states.js:410`），
并**自动唤醒发起席位**（`lib/tools.js:4098`）。

### 8.6 人工介入：三个工具，两种 `decision_kind`

```

**`pipeline_human_request` 参数**（`lib/tools.js:4131-4148`）：

### 8.7 解冻 / 冻结（误报冻结怎么解）

**症状**：任务莫名其妙变成「已阻塞」，`pipeline_status` 的 `liveness.silent[]` 里有席位。

**三条恢复路径**（按推荐顺序）：

| 路径 | 命令 | 会发生什么 |
|---|---|---|
| ① **重派同一席位**（推荐） | `pipeline_dispatch { task_id, role, seat, reassign: true }` | **先自动 `unblock`**（回到阻塞前的状态）再派；**不消耗打回预算**（`lib/tools.js:1934-1957`） |
| ② **手动解冻** | `pipeline_transition { task_id, event: "unblock" }` | 回到 `previous_state`；若恢复点不可用 ⇒ 按任务进度**回落**并写 audit（`lib/states.js:595-634`） |
| ③ 放弃这张单 | `pipeline_transition { task_id, event: "cancel" }` | 进终态 `cancelled` |

★ **主动冻结**用 `pipeline_transition { task_id, event: "block" }`（`by: ['main','human']`，`lib/states.js:427`）。
★ **别对同一张单连按两次 `block`**：第二次的恢复点会被判不可用（`lib/store.js:1650` 已收紧为"首次才记"），
但你会在 audit 里多出两条记录。

**误报冻结怎么认出来**：查 `.pipeline/<单号>/audit.jsonl` 里那条 `transition:block` 的 `note`。
机制触发的措辞固定是 `★ 机制触发（不是人叫停）：席位失联：…`；
人主动冻的会写别的原因。然后拿 `liveness.silent[].session_id` 去看那个会话**是不是还在长**。

### 8.8 看改动：`pipeline_change_audit`

**参数**（`lib/tools.js:1526-1529`）：`task_id` / `take` / `note` / `role_token`。

* **取基线**：`take: true` —— ★ **只有计划 AI / 主对话能调**（`:1547-1553`），
  原文：「★ 基线是"没动手之前的样子" —— 谁能重设它，谁就能把已经改过的东西洗成"本来就这样"。」
  重取会留痕（`audit: baseline:take`），并**把连续不过的计数重新起算**（`lib/hashgate.js:398-414`）。
* **前后对比**：不带 `take` ⇒ 拿基线与当前状态逐文件比。

**返回值看什么**（`lib/tools.js:1531-1537`）：

| 字段 | 含义 |
|---|---|
| `verdict` | `within_scope`（全在授权面内）/ `out_of_scope`（有多改） |
| `baseline_id` | 用的是哪一版基线 |
| ★ `unauthorized` | **多改 / 改错地方**：清单外的改动 `[{ path, how }]` |
| ★ `missing` | **少改**：授权了却没动的条目 `[{ scope_id, path }]` |

★ **它不告诉你"是谁改的"**（我实读确认）：`lib/store.js:3154/3156/3161` 逐文件条目**只有路径与哈希**；
唯一带"人"的字段是**基线级**的 `taken_by`（`:3052`，指"谁取了基线"）。
所以"谁改的"要靠 `change_manifest`（**席位自报的声明**，`lib/store.js:4083`）+ 审计事件里的 `actor`
（`lib/store.js:727-728`）—— **那是两条不同层级的证据，别混**。

**做完会发生什么**：`take: true` 会改基线（写 `task.baseline_current`，`:3065`）；不带 `take` 是**只读**。

### 8.9 一份"照着走"的最小流程（主对话视角）

```
1) pipeline_task_open { requirement: "<用户原话>" }
      ⇒ 状态 pending，拿到主对话令牌

2) 派需求分析：pipeline_dispatch { task_id, role: "orchestrator", permission: "read-only", mode: "standard" }
   推状态：    pipeline_transition { task_id, event: "dispatch_orchestrator" }   ⇒ analyzing
   （★ 若角色名单里登记了主管席位，这条边会被 hub_initiate_required 拒 —— 改成由主管发起）

3) 需求位交结论后收到唤醒 ⇒ pipeline_status 重读 ⇒
   走人工确认：pipeline_human_relay → pipeline_human_reply（记用户原话）
   然后：pipeline_transition { task_id, event: "requirement_confirmed" }        ⇒ ready_plan

4) 派计划：pipeline_dispatch { task_id, role: "planner" } + transition dispatch_planner ⇒ planning
   计划位交 plan（自检 verdict=ok）后：transition planned                        ⇒ ready_dev

5) 取基线后派编写：pipeline_change_audit { task_id, take: true }
                   pipeline_dispatch { task_id, role: "writer", seat: "writer#1", permission: "workspace-write" }
                   pipeline_transition { task_id, event: "dispatch_writer" }     ⇒ developing
   编写交 dev_to_test 后：transition dev_submitted（★ 只有 writer 能发）        ⇒ ready_test
   （★ 哈希闸门不过 ⇒ 直接打回，不消耗测试预算；连续 3 次 ⇒ 自动交人工并拒收重交）

6) 派测试：pipeline_dispatch { task_id, role: "tester" } + transition dispatch_tester ⇒ testing
   test_passed ⇒ ready_test→ready_review ；test_failed ⇒ returned_to_dev

7) 派审核：pipeline_dispatch { task_id, role: "reviewer", permission: "read-only" } + transition dispatch_reviewer ⇒ reviewing
   review_ok（★ 只有 reviewer 能发）                                            ⇒ passed

8) 关单：pipeline_close { task_id }   ⇒ closed（close_gates 组合闸必须全过）
```

★ 每一步之后**先 `pipeline_status`，再推下一个 `event`** —— 这就是 8.4 那条纪律的实操形式。

## 九、排障手册（按现象查）

> 每条的格式：**现象 → 根因 → 怎么办 → 证据在哪看**。
> 所有证据路径以 `T-…` 代指 `.pipeline\<单号>\`。

### 9.1 任务卡住不动

* **现象**：状态好几十分钟不变，`pipeline_status` 的"下一步合法事件"一直指向同一个动作。
* **根因**（按概率排序）：
  1. 席位**死了或没人在动**（第 9.2 条）；
  2. 有一条**守卫没过**（每次被拒都会给拒码与原文）；
  3. 处在**等待态**（`awaiting_human` / `awaiting_clarification`）—— 那是**正常**的，"等谁"写在状态名里。
* **怎么办**：
  * 先 `pipeline_status { task_id }` 看 `liveness.silent[]` 与 `next_actions`（可直接照抄的命令）；
  * 若在等待态：`pipeline_human_relay`（列收件箱）/ `pipeline_clarify_reply`（需求分析出裁定）；
  * 若被守卫拒：照拒码改（每个拒码的原文都写了"下一步"）。
* **证据在哪看**：`T-…\audit.jsonl` 最后 20 行（按 `at` 排序）；`pipeline_status` 的 `hash_gate` / `liveness` 两栏。

### 9.2 席位被判失联

* **现象**：任务变成「已阻塞」，`audit.jsonl` 里多一条 `transition:block`，
  note 是 `★ 机制触发（不是人叫停）：席位失联：… 静默阈值 5 分 …`。
* **根因**：四条判据同时成立（第六章 6.1）。**最常见的是"它其实在干活"**——
  席位在写报告/读源码的几分钟里不产生台账事件，而"会话文件在增长"这条证据
  在**旧版**里恒等于零（`lib/liveness.js:121-129` 的诊断）。
* **怎么办**：
  1. **先核对是不是误报**：拿 `liveness.silent[].session_id`，
     去 `<DSH 会话根>\<bucket>\<sessionId>\session.v4.jsonl.zstd` 看 `size` / `mtime` 是不是刚才还在长；
  2. 是误报 ⇒ `pipeline_transition { task_id, event: "unblock" }`，然后**催一下那个席位**
     （`pipeline_dispatch { task_id, role, seat, notify_only: true, note: "…" }`）；
  3. 真死了 ⇒ `pipeline_dispatch { task_id, role, seat, reassign: true }`（会自动解冻、不消耗打回预算）。
* **证据在哪看**：
  * `T-…\audit.jsonl` 的 `transition:block` 行（含 `from` 与 note）；
  * `T-…\task.json` 的 `liveness.escalations[]`（每次升级的时间与席位）；
  * `task.json` 的 `liveness.samples` —— ★ **如果这个键从来没出现，说明活动采样一次都没成功**
    （`lib/liveness.js:126-128` 记的正是这个形状）。

### 9.3 令牌失效（重启后）

* **现象**：席位调用报 `role_token 无效：…` 或 `缺少 role_token`。
* **★ 两种原因文字上是分开的**（这正是 2026-10-11 修的一个文案缺陷，`lib/tokens.js:84-128`）：
  * `role_token 已过期：…` ⇒ **真超时**（TTL 从铸造起算，默认 2 小时，`lib/tokens.js:27`）；
  * `role_token 无效：本机令牌表里**没有**这枚令牌` ⇒ 通常是 **DSH 刚重启**（令牌表是进程内存态，**所有**令牌包括主对话那枚**必定全部丢失**），
    或者字符串抄错 / 被截断 / 属于另一个工作区。
  * 原文（`lib/tokens.js:90-92`）：「措辞纪律：**「表里没有」这一支里不许出现"过期"二字**。」
* **怎么办**（`lib/tokens.js:118-126` 给的恢复路径）：
  1. 主对话也没了身份 ⇒ `pipeline_task_open { task_id: "<任务id>", reattach: true }`；
  2. 让主对话 `pipeline_dispatch` 重新派活铸新令牌。
  * 令牌形状：`PT-` + 24 位十六进制 = **27 个字符**（`lib/tokens.js:126`）。
* **证据在哪看**：`T-…\task.json` 的 `history` 里有没有一条 `reattach`；
  `T-…\audit.jsonl` 里 `action = "reattach"` 那一行。
  ★ 真单实证：`T-20261012-8cdee0` 在 `2026-10-13T09:50:11Z` 走过这一步。

### 9.4 哈希闸门 `undeclared`（声明不实）

* **现象**：`pipeline_status` 的 `hash_gate` 显示 `blocked`，拒码 `HASH_GATE_FAILED`，
  逐条给出 `undeclared_change`（动了但没在改动声明里报）。
* **根因**（四种之一，`lib/hashgate.js:53-58`）：
  ① 新增清单外文件；② 修改清单外文件；③ 删除清单外文件；④ **声明不实**。
  ★ 第四种最常见，而且**未必是编写干的**：`store.changeAudit()` 算的是"基线以来的所有变化"，
  它**没有归属信息**（`lib/hashgate.js:69-71`）。机器产物那一类已经在**今晚**被豁免（见 4.4）；
  但**别的角色**在同一时间段改的文件仍会算到"本单"头上。
* **怎么办**：
  1. 看拒绝原文里的**逐条路径 + 基线哈希 + 实际哈希**（`lib/hashgate.js:275-328` 的 `renderGateRejection` 就是为这个写的）；
  2. 三条出路（原文 `:325-326`）：① 撤回越界改动；② 走 `pipeline_clarify_request`；
     ③ 走 `pipeline_roster_request` 拿**新授权**再交；
  3. 如果基线取早了（含**与本单无关**的基础设施改动）⇒ 让计划 AI 或主对话
     `pipeline_change_audit { task_id, take: true }` 重取基线 —— **计数会重新起算**（`lib/hashgate.js:398-414`）。
* **★ 注意两个副作用**：
  * **连续 3 次不过 ⇒ 机制自动交人工**，并在用户答复前**拒收**同一任务的再次提交（拒码 `HASH_GATE_ESCALATED`，`lib/store.js:3689-3704`）；
  * 升级期间**任何人**都不能替它盖章（`station_confirm` 也拒，`lib/store.js:3719-3731`）。
* **证据在哪看**：`T-…\audit.jsonl` 的 `gate:hash` 行（含 `baseline_id` / `streak` / `pass`）；
  `task.json` 的 `hash_gate` / `hash_gate_checks[]` / `hash_gate_streak` / `hash_gate_escalation`。

### 9.5 交付被拒收

* **现象**：`pipeline_handoff` 返回 `ok:false`，summary 里写「这条交付**没有**被接收，但**内容已留档**」。
* **根因**：三类 —— ① 任务状态不允许；② 跳步（`HANDOFF_STEP_SKIPPED`）；
  ③ 字段校验失败（`BAD_HANDOFF`）或角色越权（`ROLE_NOT_ALLOWED`）。
* **怎么办**：照拒码改。★ 分清"这条会不会被留档"：
  **只有 ①② 会写进 `task.rejected_deliveries[]`**（`lib/tools.js:2365-2366`）；
  ③ 那两类只留在审计与那次调用的返回值里（未命中留档分支）。
* **证据在哪看**：`T-…\task.json` 的 `rejected_deliveries[]` ——
  每条含 `delivery_id`（`RD-…`）、`state_at_submit`、`payload`（超 20,000 字符只留前一段）、`recall`；
  审计里的 `delivery:rejected` 行。
  ★ **注意**：`recall` 里写的「`pipeline_status` 的「被拒收的交付」一节」**目前并不存在**（见第十一章）。

### 9.6 投不出去

* **现象**：某个动作返回 `ok:false`，说"**没投出去**"。
* **★ 先纠正一个说法**：本手册的任务书里提到的错误串 **`no-live-request` 在代码里不存在**
  （我对 `lib/*.js` 与 `index.js` 做过大小写不敏感的整包搜索，`no-live` / `no_live` / `noLive` **零命中**）。
  真实的"投不出去"有**四类**，各有各的码与文案：
* **四类与各自怎么办**：

| 类别 | 码 / reason | 出现在哪 | 怎么办 |
|---|---|---|---|
| 唤醒没有主会话可投 | `wake:skipped` + `reason: "no-main-session"` | `lib/wakeup.js:1175` | 让主对话**先调任意一个 pipeline 工具**（会把会话登记进 `contacts.main`） |
| 唤醒拿不到稳定身份 | `wake:skipped` + `reason: "no-stable-identity"` | `lib/wakeup.js:1326` | 看账本 `unresolved`；巡检会再叫一次 |

### 9.7 唤醒报"叫不醒"

* **现象**：用户答复了人工请求 / 澄清裁定落地了，但返回里写着
  「⚠ **裁定已落地，但叫不醒发起席位**「…」—— 这是**看得见的失败**（不是静默）」（`lib/tools.js:4462`）。
* **根因**：`wakeResumedSeat` 从**派活台账**里找那个席位的会话，找不到或投不进去
  （`lib/tools.js:4451`）。两个常见子因：
  ① 台账里没有这个 role/seat 的记录（`lib/tools.js:529-533`）；
  ② 台账里没有会话 id（`session_id` / `agent_id` 都是空的，`:534-538`）。
* **怎么办**：返回体里**已经给了等价路径**（`:1929-1931` 那一组）：
  重派同一席位（`reassign: true`）/ 查派活台账（`pipeline_status`）/
  若会话已经不在了 —— 「这条**只能由用户**在 GUI 里处置（插件不替你删会话）」。
* **证据在哪看**：`audit.jsonl` 的 `seat:wake-delivered` / `seat:wake-failed` 行（含 `key` / `request_id` / `target_session`）；
  `wake-ledger.jsonl` 里 `t: "seat-wake"` 的行；以及"已投递未接管"清单
  （`pipeline_status` 的 `liveness`，或 `wakeup.pendingSeatDeliveries`）。

### 9.8 守门误拦

* **现象**：某个会话做一件看起来正当的事，被拒，理由却是别的规则。
* **★ 先接受一个前提**：**shell 侧是字符串匹配的 best-effort，不是保证**（`lib/guard.js:49-51`）。
  所以"误拦"与"漏拦"都可能发生，而且同形状命令**可能一次放行、一次拒绝**（`:1128`）。
* **已知误拦的两种形状**：
  1. **按目录前缀判"读代码"**（`:1131-1133`）：只要路径落在项目根下就算读代码。
     ★ **这一处已经改过**（改成按**文件身份**判，`:1146-1157`），但改后效果**未做活体验证**。
  2. **同步索引未命中 ⇒ 判据整段跳过（fail-open）**（`:599-606`）——
     那不是误拦，是**漏拦**，且会留痕（`onMissingTask`）。
* **怎么办**（三个开关，`lib/guard.js:1214-1216` 点名）：
  `guardShellTools` / `guardMainReadsCode` / `guardWriterRunsTests`（可把对应那层整体关掉）；
  另有 `guardHubStandby`（`lib/guard.js:1402`）与 `guardHashGate`（`:1366`）。
  关掉之前先想清楚：**关的是判据，不是提醒**。
* **证据在哪看**：拒绝原文里会带出判据名与"说明：shell 侧是**字符串匹配**的 best-effort 判据…"（`:1254-1255`）；
  失败后 `guard` 自己的 warn（`guard-factory.js:51-70` 的"索引未命中"留痕）。

### 9.9 `notify_only` 崩（`ReferenceError: Cannot access 'seat' before initialization`）

### 13.5 一句话总结

> **这套插件把"谁该干什么"编码成了四类可机械复核的判据**：
> 角色能力表（谁不能产出什么）、状态转移表（谁有权触发什么）、
> 守门作用域（谁能在哪里写）、哈希前置闸门（改动面是否等于授权面）。
> 它的**长处**是判据可复算、拒绝原文给下一步、失败可见（审计 + 账本 + 巡检三层兜底）；
> 它的**已知短处**在第四章与第十一章写得很清楚：
> **shell 侧只是字符串匹配的 best-effort**，而**只读导出里有三处判据名与实现漂移**。
