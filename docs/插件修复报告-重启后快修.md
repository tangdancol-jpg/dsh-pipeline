    `"undefined"` 去匹配席位，**永远匹配不上**（这正是旧代码 `seat === undefined ? null : seat` 的意图）。

## ② 「正在写交付」的席位被判失联并冻结 —— **已修**

### 现象
**T-20261012-8cdee0 = 6 次**误冻（= 本单 `liveness.escalations` 长度 6；`T-20261011-214043` = 7 次、`T-20261012-6884af` = 3 次，逐单数字以 `.pipeline\<单号>\task.json` 的 `liveness.escalations` 为准），全部砸在「席位写完报告、正要交交接物」的几十秒。
证据：`T-20261012-8cdee0\audit.jsonl` 的 6 条 `transition:block`（`note` 含"机制触发"）。

### 根因（**两层，都实测复核过**）

**第一层：活动采样从来没成功过一次。**
实测读 `T-20261012-8cdee0\task.json`：

```
liveness keys = [ 'escalations', 'quiet' ]      ← 连 samples 键都没有
sample keys   = []
6 条 escalation：evidence[0].activity.known=false、sample_at=null、activity_known=false
```

`lib/store.js` 的 `sampleSessionActivity()` 只认 `DSH_SESSIONS_DIR` / `DSH_HOME`
两个环境变量；取不到就 `root === null` 早退，并**硬编码** `gate_applicable: false`
⇒ 采样恒为空 ⇒「会话文件在增长」这条证据**恒等于零**，退回老三条台账判据、一次安静即冻结。
（与既有只读诊断报告 `诊断报告-B2会话活动判据为什么没拦住.md` §3.3 的排除法结论一致；本次是独立复核。）

**第二层：拿到样本时也判不出来。**
`activityOfSamples` 把「两次采样跨窗」与「首次采样」都报成 `known: true`
⇒ 在 `seatLiveness` 里**绕过了"连续确认"门** ⇒ 一次观察即冻结。实测复算：

```
activityOfSamples({size:563327}, {+13min, size:575960})   ← 真实 +12633 字节
改前 → {"known":true,"grew":false,"reason":"两次采样间隔 13 分 超出窗口 2 分"}
```

> 该夹具的两端数字取自 **`T-20261012-6884af`**（本单 `audit.jsonl` 2026-10-12T14:44:15Z 的 `transition:unblock`，`task.json:1048` 同文）：被判失联的编写席会话 `session-…` 的日志在 13 秒内由 `563,327 B` 增至 `575,960 B`。

采样只在「任意角色的下一次工具调用」发生；席位写报告那几分钟**没人调工具**，
上一次采样早已过期 ⇒ 差值窗口用不上，「正在写」被判成「没在长」。

**第三层（同一条判据上的独立缺陷）：** `quiet_streak` 在 pending 分支被写成 `0`
⇒ 计数器永远凑不满 `confirmations` ⇒ 门一旦开着，机制**一个席位都冻不掉**（等于静默关掉检测）。
