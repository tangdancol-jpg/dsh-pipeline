## 一、核实（调用点与影响路径）

### 1. 假设还在不在 —— 在，改前实测就是这个形状

`lib/wakeup.js:436`（改前行号）`actorKeyOf`：非空 seat 一律拼成 `${role}#${seat}`，**没有**「席位名 === 角色名」这一支：

```js
const s = typeof seat === 'string' && seat.length > 0 ? String(seat).replace(/^[a-z_]+#/, '') : ''
return s.length === 0 ? r : `${r}#${s}`
```

改前探针（`node` 直接 import 该模块）：

```
actorKeyOf("tester","tester") = "tester#tester"      ← 缺陷
actorKeyOf("tester",null)     = "tester"
actorKeyOf("writer","writer#2") = "writer#2"
ledgerIdentityScoped(actor=tester) = {"disc":null,"source":"none","key":null,"author":null,"replayKey":null,"candidates":1}
```

最后一行是**后果**：台账里明明有那条 tester 交的实体（`candidates:1`），却被作者判据丢掉了。

### 2. 谁在调它（4 处，全部在 `lib/wakeup.js`）

| 调用点 | 位置（改后行号） | 干什么 |
| --- | --- | --- |
| `ledgerCandidates` 的 `author` | `lib/wakeup.js:621`（handoff）、`:624`（artifact）、`:627`（record）、`:630`（clarify）、`:633`（human） | 台账每一行「**是谁交的**」都由它算出来 |
| `wake()` 里本次事件的执行者 | `lib/wakeup.js:1348` | 与台账 author 做「作者对齐」；也进审计与正文 |
| `seatDeliveryKey` | `lib/wakeup.js:1773` | 席位侧反向投递的键 `…|seat:<席位>|<请求 id>` |
| B 路的记录性引用 | `lib/handoff.js:2020-2026` | 只如实记录、声明不越界改（本次未动该文件） |

### 3. 影响路径（为什么现场不炸、只在"账本重建"发作）

- 台账行 `from_seat="tester"` 是**现在**的正常写法：`lib/handoff.js:2031-2042` 的 `resolveHandoffSeat` 第 ③ 档「单席位角色 ⇒ 席位名就是角色名」（与 `liveness.seatKey(role, seat) = seat || role` 同源）。⇒ 由它算出的 author 是 `tester#tester`。
- 实时令牌那侧算出的 actor 是 `tester`：`lib/intercept.js:631 actorSeat: actor.seat`（`tools.js` 各处同形），而 `lib/tokens.js` 明确「非编写角色为 null」 ⇒ `actorKeyOf('tester', null) = 'tester'`。
- 两者在 `lib/wakeup.js:693-698` 的**作者对齐**判据上相遇：

  ```js
  const cands = liveLedgerCandidates(kind, task)
  if (actor.length > 0 && c.author.length > 0 && c.author !== actor) continue   // ← 自家实体在这里被丢掉
  ```

  ⇒ 候选全被跳过 ⇒ 返回 `{disc:null, source:'none'}` ⇒ `wake()` 走 `reason:'no-stable-identity'` 的「看得见的失败」（`lib/wakeup.js:1390` 一带），**该叫不叫**。
- 正常交付不经过这条路：`eventIdentityFor` 第 ① 档直接从工具返回值取 `handoff_id`（`lib/wakeup.js:746-770`）⇒ 所以影响面**只在"账本重建"这一路**，与 B 路的判断一致：
  - `lib/wakeledger.js:181-237` 的 `rebuildEntriesFromTask`（尤其 `:201-206` —— 那里有一份**同源副本** `actorOf`，同样没有「席位名 === 角色名」这一支），重新算出来的键是 `…|tester#tester|…`；
  - 线上实时算的是 `…|tester|…` ⇒ **重建判不出重复**，历史账本会被当成"没播过"而重播一次（A1/A19 要治的正是这个）。

## 二、修法与兼容策略

### 1. 硬化：席位段的换算**只留一处**，三条口径

新增 `lib/wakeup.js:275 seatSegmentOf(role, seat)`（`wakeKeyOf` / `actorKeyOf` / `legacyWakeKeyOf` 共用）：

| 输入 | 席位段 | 结果 |
| --- | --- | --- |
| `writer` + `writer#1` / `writer#2` | `1` / `2` | `writer#1` / `writer#2`（**席位保留**） |
| `writer` + `null` / 空 | `` | `writer` |
| ★ `tester` + `tester` | `` | `tester`（**视作无席位**，本轮硬化） |

- `lib/wakeup.js:525 actorKeyOf` —— 就是这一条硬化（原来的假设删掉，改走共用换算）。
- `lib/wakeup.js:300 wakeKeyOf` —— **同一份换算**。为什么必须一起改：`ledgerIdentityScoped`（`:716-724`）拼探测键时是把 actor 归一后再交给 `wakeKeyOf` 的；若 `wakeKeyOf` 仍按旧口径拼，同一个文件里就会出现「探测用 `tester`、实际投递用 `tester#tester`」两种拼法，去重与留痕从此对不上。带席位的调用（`writer#1`）逐字不变（`tests/t14-fix-check.mjs:260` 那条既有断言照旧成立）。

### 2. 兼容：旧账本**不迁移、不改写**，读取侧**新旧都认**

- `lib/wakeup.js:335 legacyWakeKeyOf(spec)` —— 算出「同一把交付键在**旧口径**下可能写成的那把」（`角色#角色`）；真有席位的键（`writer#1`）**返回 `null`**（那种键旧口径算出来一模一样，没有第二种形态）。
- `lib/wakeup.js:354 deliveredKeyFormIn(ledger, key, legacyKey)` —— 读取侧探两把，返回**命中的那一把**（报出账本里真实的那一行，便于配对可读）。
- 两个**读取点**接上它（写入侧一律只用新形态）：
  1. `lib/wakeup.js:716-724` `ledgerIdentityScoped` 的「已播过 ⇒ 重放」判定（`replayKey` 报命中的那一把）；
  2. `lib/wakeup.js:1433` + `:1472-1490` `wake()` 的跨进程去重（`ledger.deliveredEntry` 也按命中形态取；审计多记 `matched_key` 与 `legacy_form`，与账本行配对可读）。
- 内存投递表（`lib/wakeup.js:1191`）不接别名：它只装本进程写下的**新键**，旧形态只可能来自盘上的历史行。
- **未动 `lib/wakeledger.js`**（别人在改它）：它那份 `actorOf` 副本（`:201-206`）仍会写出旧形态键 —— 这正是"读取侧同时认"要兜的场景；哪天那份副本统一到新口径，读取侧不用再改（新形态照旧命中）。
- **如实列一条残余（不影响判据）**：`seatDeliveryKey`（`lib/wakeup.js:1773`）随 `actorKeyOf` 变成 `…|seat:tester|…`，而 `lib/tools.js:497` 那份实时口径仍写 `…|seat:tester#tester|…`。两侧不靠这串字符配对：席位投递的**接管**读的是账本里存下来的 `e.key`（`lib/wakeledger.js:574-576`），**清单过滤**读的是 `seat` 字段（`lib/wakeledger.js:583`）—— 两者都与拼法无关；且本仓库内 `seatDeliveryKey` 只有 `tests/wake-channel-check.mjs:386` 一个消费者（`writer#1`，前后逐字不变）。
