## 一、核实结果（两处现状 + 实测原文）

### ① 入口【悬空】—— 属实，且比"被拒"更糟：**主管席位在任何阶段都派不出来**

**证据 1（工具面）**：`lib/guard.js:492` 的 `PIPELINE_TOOL_ROLES` 里

```js
pipeline_supervise: ['supervisor'],
```

主对话调它被守门拒，原文：

```
[pipeline] 角色越权被拦下。工具：pipeline_supervise 允许角色：supervisor 当前角色：main 原因：本工具被限定给上列角色。
```

**证据 2（状态机面）**：`lib/states.js` 的 `TRANSITIONS`

```js
{ from: ST.PENDING, event: 'supervisor_initiate', ... by: [ROLE.SUPERVISOR], guard: 'hub_initiate' }
```

`main` 代发连第二道都到不了 —— `applyTransition` 的 `by` 名单直接拒。
所以 `boundaries.js` 的 `initiator_roles: ['supervisor']` 是**准确**的，问题不在它。

**证据 3（真正的死结 —— 派活面）**：`lib/tools.js` 的引导步白名单

```js
if (task.roster === null) {
  const planningStage = task.state === ST.READY_PLAN || task.state === ST.PLANNING
  const allowedBootstrap = planningStage ? [ROLE.PLANNER] : [ROLE.ORCHESTRATOR]
```

新单上 `roster === null` ⇒ **只能**派需求分析。两次实测原文一致：

```
任务 T-20261014-hello02 还没有角色清单（当前状态：待分配）。
这个时候唯一能被派出去的角色是：需求分析。
★ 顺序是：需求分析（出任务卡 + 不清楚处清单）→ **用户确认** → 计划（出角色清单）。
主对话不自行判断要调几个 AI。
```

而 `supervisor` 想进名单，只能由 **planner** 产出清单 —— planner 的唯一唤醒点是 `diagram_confirm`（唤醒点 B），
唤醒点 B 又要求枢纽**已经发起**。**闭环死锁**：

```
派不出 supervisor → 发不起枢纽 → 架构位/计划位不登记待机 → planner 产不出清单 → supervisor 进不了名单 → 派不出 supervisor
```

⇒ **结论与用户口径一致**：入口应当是「主对话 → 主管」。（需重启后复验）

### ② 少一环确认 —— 属实

改前表上从「架构图完成」到「交计划」只有一跳（`lib/states.js` 改前原文）：

```js
{ from: ST.ARCH_CONFIRM, event: 'supervisor_confirm_diagram', to: ST.STANDBY_PLAN, by: [ROLE.SUPERVISOR], guard: 'hub_station_diagram_confirm', note: '★ 第②道确认（主管确认架构图满足要求）＋ **唤醒点 B**：计划位到点开工' },
```

即「架构图 → 主管确认 → 计划」，**表上不存在** `arch_confirm → standby_plan` 之外的任何中间站；
用户原话要求的「需求 agent 确认」「主管二次确认」两个确认点**一条判据都没有**。⇒ 属实。

### ③ 顺带核实到的一条"与用户原话不符"（如实报出）

- 用户原话第 9 跳：「无问题后将**架构agent**递交计划agent」—— 递交者是**架构位**。
  而既有边 `dispatch_planner` 的 `by` 是 `['main']`，我**没有**改它。
  **理由**：把架构位加进这条 `by` 名单等于让架构位拿到"派活"这一权限面（越权放行），
  与本单硬约束「不得新增任何越权放行」直接冲突；且既有自测把 `dispatch_planner` 的形态钉住了。
  本单按"**谁有权触发这一跳**"保持 `main`，把新增的**确认点**（②b/②c）插在它**之前** ——
  用户要的"无问题后才交计划"这个**语义**由两个确认点的硬闸门保证（判据见 §三/§四）。
- 用户原话第 6 跳说"架构agent完成后发给主管agent"，而既有表里 `diagram_submitted` 由 **diagrammer** 触发
  （`roles.js` 里 architect 出"该怎么写"的文字方案、diagrammer 出图；发布单里用户已裁定过这一分工）。
  本单**不动**这个分工。

## 二、设计

### 2.1 修入口：**二选一取 (a)**（允许主对话在流程最初那一刻把任务递给主管）

**为什么不用 (b)**（允许 main 调 `pipeline_supervise{action:"initiate"}`）—— 不是偏好，是**被既有判据挡住**：

`tests/gate-states-check.mjs` 的「A 发起面」逐字断言：

```js
rec.add('A 发起面', '★ 主管的具名动作**不是** main 的工具：`pipeline_dispatch` 的 by 名单里没有 supervisor',
  !TRANSITIONS.some((x) => x.event === 'supervisor_initiate' && (x.by ?? []).includes('main')), '')
```

给 `supervisor_initiate` 的 `by` 加 `main`（或放宽工具白名单）会**直接改掉这条既有判据的期望值** ——
本单硬约束明令禁止（"不得删既有测试、不得放宽断言、不得改期望值"）。
且 (b) 单独也不够：即使 main 能发起，**主管席位仍然派不出来**（§一 证据 3），枢纽照样启动不了。

**取 (a)：主对话走自己的一条边界事件**（新增一条 `TRANSITIONS` 表项，不新开工具、不动任何工具-角色白名单）：

```js
{ from: ST.PENDING, event: 'handoff_to_supervisor', to: ST.PENDING, by: ['main'], guard: 'main_handoff_to_supervisor', ... }
```

它是**自环**（pending → pending）：用户原话里**推进流程的是"主管拉起三席"，不是"递单"这个动作**。
状态不变的边在表上有先例（`human_request` 的 `from:'*'`；`submitHandoff` 里通用规则"目标状态与当前状态相同 ⇒ 不做这次迁移"）。

#### ★ "凭什么放行"（主对话发起时依据什么）

判据体：`lib/store.js` 的 `checkPrecondition` → `case 'main_handoff_to_supervisor'`。**五条同时成立**：

| # | 判据 | 拒绝码 |
|---|---|---|
| 1 | 调用方是 `main`（状态机 `by:['main']`；`pipeline_transition` 本来只给 main/human，human 被这条 by 名单挡住） | `BAD_TRANSITION` |
| 2 | 状态 = `pending`（待分配） | `HUB_HANDOFF_NOT_FIRST_MOMENT` |
| 3 | `roster === null`（还没有角色清单） | `HUB_HANDOFF_AFTER_ROSTER` |
| 4 | `handoffs.length === 0`（活儿还没开工） | `HUB_HANDOFF_AFTER_WORK` |
| 5 | `hub.entry` 不存在（递单是一次性动作） | `HUB_HANDOFF_ALREADY_DONE` |

#### ★ "枢纽必须激活在哪一层"

**最外层 —— 只能落在 `pending`（待分配）这一层**：判据 2+3+4 合起来要求的是**零工作量的新单**
（没有状态推进、没有交接物、没有角色清单）。任何一项出现，这个入口**永久关闭**。
只读导出里写死这一句：`boundaryManifest().supervisor_hub.entry.activation_layer`。

#### ★ "不得顺带放宽别的角色的可派范围"

递单之后，引导步白名单**只**多出 `supervisor` **一席**，而且是**替换**掉需求分析那一席（不是追加）：

```js
const handedOver = task.state === ST.PENDING && task.hub?.entry !== null && task.hub?.entry !== undefined
const allowedBootstrap = planningStage ? [ROLE.PLANNER] : handedOver ? [ROLE.SUPERVISOR] : [ROLE.ORCHESTRATOR]
```

其余角色（orchestrator / architect / planner / tester / writer / reviewer / diagrammer / …）**一个都没进来** ——
反例逐条断言（§四【E】）。

**另有一处必要且最小的配套**：`pipeline_dispatch` 的**需求档硬闸**（"没有留档就不许开工"）豁免名单
原文是 planner / orchestrator / archivist，现补上 **supervisor**（第 4 条）。
理由与那三条**逐字同一条**（原注释就写着"卡它就死锁"）：需求档是需求位/留档位的产物，
卡住主管 ⇒ 派不出主管 ⇒ 发不起枢纽 ⇒ 没有需求位 ⇒ **永远产不出需求档**。
主管是控制位（不写实现、不跑测试、不判通过），"开工"对它本来就是另一个意思；
豁免**只是**打开这条死锁，没有给它任何新的写入面或判定面（写入面仍由 `roles.js` 的 `writes` 管）。

### 2.2 补确认环：两个确认点，**不新开第二套站点**

新增两个确认点（与既有站点**同构**）：

| 确认点 | 站点名 | 确认方 | 判据名（`store.checkPrecondition`） | 放行哪一跳 | 落点 |
|---|---|---|---|---|---|
| ②b | `arch_need_confirm` | `orchestrator`（需求位） | `hub_station_arch_need_confirm` | `need_confirm_diagram` | `arch_confirm → arch_need_confirm` 之后的 `arch_need_confirm → arch_reconfirm` |
| ②c | `arch_reconfirm` | `supervisor`（主管） | `hub_station_arch_reconfirm` | `supervisor_reconfirm_diagram` | `arch_reconfirm → standby_plan` |

新的边（`lib/states.js`）：

```
arch_drawing --diagram_submitted--> arch_confirm
arch_confirm --supervisor_confirm_diagram--> arch_need_confirm      ← 第②道：主管首判 ⇒ 转交需求位
arch_need_confirm --need_confirm_diagram--> arch_reconfirm          ← ②b：需求位确认（交 station_confirm 即推进）
arch_reconfirm --supervisor_reconfirm_diagram--> standby_plan       ← ②c：主管二次确认 ＋ 唤醒点 B
standby_plan --dispatch_planner--> planning
```

**同构性（逐项对齐既有站点，没有第二套机制）**：

| 维度 | 既有站点怎么做 | ②b/②c 怎么做 |
|---|---|---|
| 事件形状 | 一条 `TRANSITIONS` 表项 + 一个 `guard` 名 | 同 |
| 守卫开关 | `store.checkPrecondition` | **同一个** switch |
| 判据体 | `hubStationGate(task, station)` | **同一个函数**，只换站点名 |
| 留痕载体 | `station_confirm` 交接物（`reason` / `basis_refs≥1` / 脱敏 `basis_digest` 由既有校验器强制） | **同一张 schema**，枚举里多了两个站点名 |
| 审计 | `audit.jsonl` 的 `transition:<事件名>` | **同一份** |
| 预算读法 | `hub.station_rejects[station]` | 同一套读法（本单**不新增否掉回边**，既有四条回边一个字节没动） |
| 绑目标 | 第②道绑 `architecture_diagram` 的 handoff_id | **同一份图的同一个 handoff_id**（换图即作废） |

**顺序即判据**：`arch_confirm` 上**不存在**直达 `standby_plan` 的边 ⇒「第②道一次点头就交计划」在新口径下**无路可走**。

**唤醒点 B 的触发跳改了**（用户口径："**无问题后**将架构agent递交计划agent"）：
从 `supervisor_confirm_diagram` 搬到 `supervisor_reconfirm_diagram`。
唤醒点常量、待机名册、产物面三条判据**一个字没动**，只是触发它的那一跳变了。
