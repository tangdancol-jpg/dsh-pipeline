### 2. 架构图前置（需求确认后先出架构图 → 主管确认 → 才交计划）

- **需求原话**（L14 / L30）：「需求确认后 → **先出架构图** → 主管确认「是否满足要求」 → **才**交计划（与现行顺序「计划 → 架构 → 安全 → 编写」不同 ✗）」。
- **怎么实现**：
  - 状态链插入 `supervising → arch_drawing → arch_confirm → standby_plan`，**表上不存在 `analyzing → planning` 的边**（"先出计划"无路可走）。
  - `lib/store.js → checkHubHandoffAgainstState()`：枢纽任务里 `architecture_diagram` 的合法状态面**整体前移**到 `arch_drawing` / `arch_confirm`；编写交付之后再交会被 `HUB_DIAGRAM_AFTER_WRITE` 拒。
  - 架构图产出经 `hubAdvanceFor()` **自动**推进到 `arch_confirm`（不需要任何角色调 main 的迁移工具）。
  - 跳步即拒：`hub_plan_woken`（计划位未唤醒 ⇒ `HUB_PLAN_NOT_WOKEN`）。
  - 重画限 1 次：`hub_diagram_rework_budget`（`HUB_DIAGRAM_REDRAW_EXHAUSTED`，拒绝原文指向"升给用户"）；用尽后的唯一出路是 `pipeline_supervise action=escalate_user`（走**既有**的 `human_request` 两级梯）。
- **判据落在**：`states.js TRANSITIONS`（**表上不存在那条边** = 最硬的一条判据）+ `checkHandoffAgainstState: HUB_DIAGRAM_FIRST` + `hub_plan_woken` + `hub_diagram_rework_budget`。
- **验证**：`gate-states-check`【B 架构图前置】8 条全 ✓（含「表上不存在 `analyzing → planning` 的边」）；`dispatch-channel-check`【E】【F】全 ✓（含「跳步即拒」「重画预算 = 1：第二次拒被拒，拒绝原文指向升给用户」）。

### 5. 待机期"不产生实质产物"（产物面三条判据）

- **需求原话**（用户口径③ / 测试要点 11.5）：「待机位在**待机期间不产生任何实质产物**（不是产物被隐藏，而是压根没产出）」；安全预审阻断项 B3：三条都要落，缺一条即不通过。
- **怎么实现**（三条**同源**、同一份数据 `task.hub.standby`）：

  2. **文件面** —— `guard.js` `hubStandbyBlocksWrite()`：待机席位写**自己目录**的报告也算开工 ⇒ 守门拒；
  3. **测试面** —— 同文件：编写交付之前 tester 跑任何测试 ⇒ 守门拒。
  - 另配**正例**（安全预审明确要求的那条）：到点唤醒之后，同样的动作**必须放行**（证明不是"把功能一起关掉"）。

### 6. 新站点纳入既有四类判据（不另起一套）

- **需求原话**（L87 / 边界条件 2）：「新增站点必须被纳入既有四类判据（三权分立 / 闸门链 / 守门作用域 / 哈希前置闸门）的判定范围，而不是另起一套」。
- **怎么实现**：

> ⇒ 本条**可以**改判定机制本体，但**只做"分账口径"层面的最小改动**，
> 并用下面的反例证明**没放松**。本报告在此**显著标注**这一授权来源。

## 1. 问题（上一个外包会话用真函数复现，本次复核一致）

- **现象**：同一张单里，**测试席跑测试**留下的 `tests/*-last-run.txt` 等机器产物脚印，
  被算成**编写席**"未申报"：实测 `unauthorized=0` 但 `undeclared=2`（那两条编写席根本没碰过）⇒ `pass=false`。
- **判定本体**：`lib/hashgate.js` 的 `hashGateVerdict()`（改前 L99-143 的"声明不实"那一段）。
- **上游**：`store.js` 的 `changeAudit()`（改后 L3131）算的是"**基线以来的所有变化**"，
  **没有任何归属信息** —— 它不问是谁写的。于是"测试台自己写的运行产物"与
  "编写偷偷改的文件"在它眼里长得一模一样。

## 2. 改法（**选项 A：排除机器产物**，最小改动；未选 B）

在 `lib/hashgate.js` 加两样东西，**只动"声明不实"那一支的口径**：

| 新增 | 位置（改后） | 作用 |
| --- | --- | --- |
| `MACHINE_ARTIFACT_BASENAMES` + `isMachineArtifactPath()` | `lib/hashgate.js:53-124` | **收得很紧的白名单**：只认 `tests/last-run.txt` 与 `tests/<套件名>-last-run.txt`（目录段必须是 `tests`）。源码 `tests/*.mjs`、夹具、其它任何文件**都不在名单里** |
| `opts.exemptMachineArtifacts`（默认 `true`）+ `unauthorizedKeys` 硬栏杆 + `ignored_machine_artifacts` 回报 | `lib/hashgate.js:186-232`（`hashGateVerdict` 内） | ① 默认豁免机器产物；② **豁免对"已被判越界"的路径一律不生效**；③ 被豁免的路径**逐条列出**，进 `counts.machine_artifacts` 与 `summary` |

- ★ `exemptMachineArtifacts: false` = **严格模式**（= 收回豁免 = 与改前逐字等价）。
  它**只能收紧、不能放松**（默认值已经是"豁免"），存在的唯一目的是让"改前 / 改后"
  能在**同一份真实数据**上做对照复现。
- ★ **`store.js` 一个字节都没改**（本条只需在判定本体上加口径；上游 `changeAudit` 保持"事实全量"，
  分账发生在消费端）。这也避开了与主管枢纽那批在 `store.js` 上的交叉改动。
- ★ **阈值、`unauthorized` 那一支、`nextHashGateStreak`、`gate:hash*` 审计全部未动**
  （可复核：越界三类的判定块改前 L83 / 改后 L149 **逐字相同**；行数 408 → 509，全部增量在新增常量与声明对账那一段）。

## 3. 改后为什么**不放松闸门**（两条硬论证，可机械复核）

1. **越界那一支一个字节没动**：`unauthorized` 仍由 `changeAudit` 按授权面算。
   机器产物只要**落在授权面之外**，照样进 `unauthorized` ⇒ 照样 `pass=false`（反例 2 实测）。
2. **豁免只对"没被判越界"的路径生效**：一条路径只要出现在 `audit.unauthorized` 里，
   它就**永远**不会被豁免吞掉 ⇒ **豁免在数学上不可能掩盖任何一处越界改动**。
   推论：豁免影响到的只可能是"**本来就在授权面内**"的机器产物。

**残余风险（如实写出来）**：若某张单把 `tests/` 授权给了编写席，而编写把一处真实改动
**故意命名**成 `tests/<随便什么>-last-run.txt`，它会落进豁免。这是选项 A 的已知代价；
选项 B（席位级写入台账，按会话/角色分账）能根治，但那是"改动更大的分账机制"——
按"拿不准就选最保守的"，本次取 A，并把这条残余风险写进代码注释与本报告。
