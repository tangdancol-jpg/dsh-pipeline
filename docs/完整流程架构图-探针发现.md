### 1.1 ★ 「跨列/跨车道边几何不可能」的完整推导

**布局前提**（本轮 `完整流程.workflow.json` 实际使用的值；`col` 是 v2 的逻辑列，渲染器再折算成像素中心）：

| 车道（自上而下） | 占用的列 |
|---|---|
| 1 `entry` | col0 = `n_intake` |
| 2 `hub` | col1 = `n_supervision` |
| 3 `seats` | col1 = `n_requirement`，col2 = `n_planning`，col3 = `n_architecture`，col4 = `n_execution` |
| 4 `gates` | col4 = `n_test`，col5 = `n_review` |
| 5 `archive` | col5 = `n_archiving` |
| 6 `closeout` | col5 = `n_closeout` |
| 7 `mech_deliver` | 机制 9 个节点（col0–col5 依布局不同） |
| 8 `mech_rule` | 令牌 / 守门 / 哈希闸门 / 状态机（col0–col4） |

**推导**（这是"只有 col0 可用"这句话的严格来源）：

一条从 `mech_deliver`（第 7 车道）向上走到某个主路径节点的边，**必须在同一列 x 上贯穿第 6、5、4 三条车道**（closeout、archive、gates），才能进入第 3 车道 `seats`（或更上面的 `entry`）。

* 第 4 车道 `gates` 占用 **col4、col5**
* 第 5 车道 `archive` 占用 **col5**
* 第 6 车道 `closeout` 占用 **col5**
* ⇒ 第 4/5/6 车道在 **col0、col1、col2、col3 上是空的**；在 **col4、col5 上被节点占死**

所以垂直走廊只可能落在 **col0–col3**。逐个看它上端能落到谁：

| 走廊列 | 上端（第 3 车道 seats / 第 1 车道 entry） | 可达？ |
|---|---|---|
| col0 | `entry` 的 `n_intake` | ✅ 可达 |
| col1 | `seats` 的 `n_requirement` | ✅ 可达 |
| col2 | `seats` 的 `n_planning` | ✅ 可达 |
| col3 | `seats` 的 `n_architecture` | ✅ 可达 |
| col4 | `seats` 的 `n_execution` | ❌ **不可达** —— 走廊必须在 col4 贯穿第 4 车道，而 col4 上正是 `n_test` |
| col4 | `gates` 的 `n_test` | ✅ 可达（只须贯穿 col4 的第 6、5 车道，这两条在 col4 是空的） |
| col5 | `gates` 的 `n_review` | ❌ 不可达 —— 走廊要在 col5 贯穿第 6 车道（`n_closeout`）与第 5 车道（`n_archiving`） |

★ **结论（可复核）**：从机制底座向上的垂直通路，**能到 `n_intake` / `n_requirement` / `n_planning` / `n_architecture` / `n_test`，唯独到不了 `n_execution` 与 `n_review`**。这不是参数问题，是"目标节点所在列在它下面的车道上被别的节点占了"。

**与实测失败的逐条对上**：

| `e_wake_seat`（`n_hostmsg`→`n_execution`，同为 col4）solver-budget-exhausted | ✅ col4 第 4 车道被 `n_test` 占死 |

| 把 `e_notify_seat` 的目标从 `n_execution` 改成 `n_test` 后就不再报错 | ✅ 正是"col4 能到 gates、到不了 seats"的预测 |
| `e_wake_main`（`n_wakeup`→`n_intake`，同为 col0）历史上一直能过（旧规格里也是这条） | ✅ col0 在三车道全空 |
| `e_clarify_reply`（`n_requirement`→`n_execution`，同在 `seats` 车道 col1→col4）第一轮就 solver-budget-exhausted | ✅ 同车道内被 col2 `n_planning`、col3 `n_architecture` 挡死，且 9 字标签（≈86px）没有合法通道可用 |

### 1.2 ★ `主管枢纽` 的走廊冲突（本轮真正绕不过去的那一处）

`hub` 车道只有 **一个**节点（`n_supervision`，col1），其余列全空 ⇒ 这条车道里**只有一条可用走廊**。而枢纽的出边与入边全部要挤这一条：

* 出：`e_agree_need`（→ `n_architecture`）、`e_confirm_diagram`（→ `n_planning`）、`e_r4_reject_diagram`（→ `n_architecture`）、`e_initiate`（→ `n_requirement`）、`e_x_reject_need` / `e_x_reject_test` / `e_x_reject_review`（三条虚线）
* 入：`e_open`（← `n_intake`）、`e_need_to_supervisor`（← `n_requirement`）、`e_diagram_submitted`（← `n_architecture`）

**因此 `e_agree_need`（枢纽→架构位）与 `e_diagram_submitted`（架构位→枢纽）是一对反向边，必然共用同一条走廊；编译器把它判成 `composition/proper-crossing`。** 而同一方向还叠了第三条 `e_r4_reject_diagram`。

★ 关键实验事实：**对 `e_agree_need` 与 `e_confirm_diagram` 这一对，穷举 128 种「路由预设 × 进出侧」组合，没有一种能让整图通过**（详见 1.3）。这排除了"再换个 side 就行"的可能 —— 冲突来自走廊数量（1 条）而不是端点选位。

### 1.4 「先降级、再按优先级加回」这个策略：写了，只跑到第一步

* **已实现**：`_probe7.mjs`（4,897 B，2026-10-14 01:47:54）。它做两件事：
  1. **阶段 1 降级**：反复 validate，每次把报错涉及的边里**优先级最低**的那条摘掉（优先级表：主路径 100 / 六条打回 R1–R6 = 90 / 三条虚线 85 / 澄清与方案 40–50 / 约束链 30 / 投递链 20–25），直到整图通过；

* **结果**：**只跑了一步就被中止** —— `_probe.json`（探针的临时输入）时间戳 01:48:05 说明它发出了第一次 validate，随后会话被停；`_probe.log.txt` 仍是上一版（probe6）留下的内容（时间戳 01:47:25），**probe7 没有产出任何结论**。
* ★ 诚实标注：**这个策略是否有效，本轮没有证据**。它看起来是对的方向（比"谁先报错就先牺牲谁"的 v3 强），但没跑完。

**对照：不做优先级保护的 v3（谁报错就摘谁）实际产出了什么**（这是反例，值得下一个会话看）：

> `_probe3`（自由推迟 + 事后重试）**确实拿到过一份整图通过、25 条边的规格**，但代价是丢掉了 10 条边，其中 **7 条是必留边**：`e_initiate`、`e_need_to_supervisor`、`e_agree_need`、`e_confirm_diagram`、`e_diagram_submitted`、`e_r1_test_to_dev`、`e_r4_reject_diagram`、`e_r5_back_to_analysis`、`e_x_reject_review`、`e_reattach_hostmsg`。

### 2.2 渲染器崩（`internal/unclassified`，524 ms）可能与哪几处有关

**先把事实钉住**（来自 `架构图-完整流程-主路径\full-flow-rejection.finalize.json`，只读引用）：

* 崩在 **`deliver` 的 `render` 阶段**，不是布局校验阶段；报错原文 `Renderer failed before emitting a structured diagnostic.`，`evidence.exitCode = 1`，`provenance: "absent"`；
* 耗时 **524 ms**（`startedAt` 17:46:04.925Z → `finishedAt` 17:46:05.450Z）⇒ 崩得很早；
* 输入是 `full-flow-rejection.candidate.json`，**25,863 B**，与我这次 `_build2.mjs` 产出的 25,862 B 只差 1 字节 ⇒ **崩溃的正是"机制底座出口搬到 col0 + 列序 A"那一版**；
* 同一份内容我用 `archify validate --layout-json` 跑时，拿到的是**结构化诊断**（`solver-budget-exhausted` / `proper-crossing`），**从未崩过** ⇒ **崩溃只出现在 `deliver` 的渲染路径上**，不在校验路径上。

**可能原因排序**（★ 以下全是假设，本轮无法再跑实验验证，请下一个会话按序排查）：

1. **机制车道内「同列 2 层堆叠」与「同列 3 层堆叠」并存**（最可能）
   `mech_deliver` 里 `n_hostmsg(-45)/n_seatnotify(+45)` 是同列 2 层，`n_wakeup(-90)/n_orphan(0)/n_reattach(+90)` 是同列 3 层，`n_liveness(-45)/n_runfail(+45)` 又是 2 层。而 `.orig` 只有**一处** 3 层堆叠（col5 的 reattach/orphan/runfail）+ 一处 2 层（col4 的 hostmsg/seatnotify），没有"一课车道里混合 2 层与 3 层"。README 明说堆叠会把这条车道切到 per-lane measurement 分支；**该分支在同车道混用不同堆叠层数时的车道高求解，可能返回值落到 `deliver` 渲染路径没处理的分支**。理由：崩溃很快、且只在渲染阶段。
2. **两条长垂直边共享 col0 且同端点收口**（次可能）
   `e_hostmsg_main` 与 `e_seatnotify_main` 从 `mech_deliver` col0 直上 5 条车道到 `entry` col0 的同一个节点 `n_intake`，而 `n_intake` 同时还挂着 `e_open`（出）。三个端点挤在同一个盒子上，渲染端口分配若取到 `undefined`，就是"没有结构化诊断直接 exit 1"的典型症状。
3. **`phases` 的 rank band 与堆叠车道交叉**（可能）
   我保留了 5 个 phase（覆盖 col0..col5），车道数 8。README 说 phase/group 框由 solved rank band 推导；若某条 band 因堆叠测高变化而为空，框计算可能除零或取空区间。
4. **`e_design` / `e_clarify_ask` 这类"同车道跨列回边"在堆叠车道下的路由缓存**（可能偏低）
   它们要在同车道上跨过占用列，需要绕行通道；渲染阶段若通道坐标未解出就可能拿到 `NaN`。
5. **showcase 渲染路径自身的 bug，与内容无关**（不能排除）
   反证：`.orig` 那份内容我只跑过 `validate`，**没跑过 `deliver`**，所以"`.orig` 不会崩"这句话本轮没有证据。

★ **建议的排查次序**：先用 `.orig` 原样跑一次 `deliver`（若也崩 ⇒ 是第 5 条，与我的改动无关；若不崩 ⇒ 用二分法把 §2.1 的 9 处节点几何 + 10 处边增删逐组还原，定位到具体那一处）。
