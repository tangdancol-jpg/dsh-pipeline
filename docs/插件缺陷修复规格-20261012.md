## B. 缺陷清单（逐条：现象 / 实测证据 / 要求）

### B1 【最高优先】计划路径被「writer 席位未声明四槽」卡死 —— 全局瘫痪
- **现象**：任何计划（`pipeline_plan`）都被同一条理由拒绝：**「writer 席位没声明四槽」**。计划 AI 试了**四种写法**（四槽分别放在编写分区 / 角色边界卡 / 层清单 / 计划顶层），四次全被同一条理由拒绝，被点名的永远是 writer 席位。
- **独立证据（更硬）**：插件**自带的正例夹具自检**（只读、临时目录、跑完即删）直接报「**内部错误（这是插件 bug）**」，给出的正是同一条拒绝理由 ⇒ **正例夹具都过不去，等于这条校验把所有人拦在门外**。
- **影响**：**所有任务都出不了计划** ⇒ 管道整体瘫痪，连修它自己的单也开不出来。
- **时间线嫌疑**：本地 `2026-10-12 20:10–20:21`，任务 `T-20261011-214043` 的编写席改过"状态/分配"相关模块并交付 `v5`。请核实是不是这批改动引入的回归。
- **要求**：`pipeline_selftest` 的正例夹具能通过；一份真计划（可用账本里 `T-20261012-6884af` 的 `handoffs/0xx-plan.json` 当样本）能产出角色清单与授权面。

### B2 失联检测误报
- **现象**：席位**高速活动**却被判「0 交接物 / 0 流水 / 0 水位自报」⇒ 机制自动把任务推到「已阻塞」。
- **实测证据（带数字）**：席位 `<session-id>` 被判失联的同一时段，其会话日志 `session.v4.jsonl.zstd` **30 秒内从 381,679 B 增至 392,396 B（+10,717 B）**；后续再测 `+14,158 B / 20 s`、`+23,207 B / 20 s`（约 1.1 KB/s）。
- **造成的实际损失**：`2026-10-12T21:16:50Z` 那次自动冻结**直接挡掉了一份已经提交的 `dev_to_test`** —— 席位自己报告"交付被拒"，账本里一条没落。
- **历史**：全账本共 6 次自动阻塞，其中 4 次被明确记为误报。
- **可用替代信号（主对话实测）**：`<session_dir>/session.v4.jsonl.zstd` 的 **size / mtime 是否在增长**。
- **要求**：补「会话还在活动」判据。**「修误判」不等于关掉检测** —— 真死掉的席位仍必须被判失联并冻结任务；**拿不到活动证据时不许只凭一次安静就冻结**。

### B3 澄清 / 人工请求裁定后，不唤醒发起席位
- **现象**：席位提 `blocking` 澄清 → 按规矩停手等 → 需求分析出裁定 → 状态**正确恢复** → **但那个停手的席位再没有任何人被叫醒**。
- **实测证据**：该席位会话自 `21:03:01` 起**完全冻结**（主对话于 21:05:36–21:06:21 观测 45 秒，size 恒为 600,357 B、mtime 恒为 21:03:01）。另测：**解除任务阻塞也不会唤醒它**（解冻后观测 45 秒，零写入）。
- **影响**：**每一次 blocking 澄清 = 永久废掉一个席位**。真单 `T-20261011-56a37e`（主管枢纽流程）整个设计围着澄清链转 ⇒ 不修则该流程跑不起来。
- **要求**：裁定落地后要唤醒发起席位（或给出等价可达路径）。**不许静默失败**：叫不醒时必须**报出一个看得见的失败**，任务也不许停在半路。（用户已裁定：**不要求自动补一个新席位**顶上。）

### B4 唤醒消息携带的状态快照过期
- **现象**：唤醒里「任务当前状态」是**生成那一刻**的快照，经会话排队投递后**已过期**。
- **实测**：当晚 6 条唤醒全部声称「已阻塞」，实际状态依次为「开发中 / 等待需求分析答复 / 计划中 / 开发中」；主对话据此发起的一次 `unblock` **被状态机拒绝**（白打一次往返）。
- **要求**：投递时重读状态，或明确标注"可能已过期，动手前请重读"。

### B5 唤醒空报 / 归因错误 / 反复重放（三条同源）
- **空报**：多条唤醒声称「交了一份交接物」「提了一条人工介入请求」，**账本里没有对应文件**。
- **归因错误**：唤醒写「谁：编写 / writer#3」，而实际新落的交接物是 `[人工介入请求] orchestrator→main`。
- **反复重放（关键）**：`T-20261011-214043|human|orchestrator|h228 → h233 → h237` 三条**内容相同、仅末段序号递增**，约每分钟一条；同类还有 `h215 / h216 / h220 / h248 / h251 / h253 / h256`。跨单复现（`T-20261012-6884af|human|orchestrator|h6`）。
  ⇒ **幂等键末段疑似"递增计数器"而不是"交付身份"** ⇒ 去重永不命中 ⇒ 同一交付被反复重放，而每次重放都携带**事件原始时刻**的状态快照（这同时解释了 B4 的空报与过期现象）。
- **要求**：幂等键用**稳定的交付身份**；播报的类型与实际事件一致；归因用真实来源角色。

### B6 席位与边界卡错配
- **现象**：`pipeline_dispatch { seat: "writer#3" }` 的回执给出的边界卡是「**席位 writer#1 · channel**」。**连续 3 次稳定复现**，不是偶发。
- **要求**：回执给出的边界卡必须是**所派席位**的；错配时报错而不是静默给错卡。

### B7 分组名取错来源
- **现象**：新派会话落进「项目分组 ……（标题 `desktop`；`root=<DSH_HOME>\profiles\desktop`）」—— 取的是**插件目录名**，不是任务的项目名。用户上一轮曾因分组名错**删掉整组**。
- **要求**：组名按**任务的项目名 / 落点目录名**取。

### B8 没有"停会话 / 催办"通道
- **现象**：主对话**停不掉空转席位**；也没有"给既有席位发一条消息"的通道（当晚只能由用户用 GUI 手动打字把席位叫醒）。
- **要求**：至少提供一条**可见的**停 / 催通道，且失败必须可见。

### B9 守门判据不稳定 + 把「读 DSH 配置/日志」误判成「读项目代码正文」
- **现象**：主对话读取 `profiles\desktop` 下的**回滚快照目录名**与**223 字节的 cordis 配置**被拦，理由「主对话不得通过 shell 读取项目代码。原因：主对话与代码正文隔离」。
- **更麻烦的**：**同形状命令一次放行、一次拒绝**（当晚 3 次拦截中出现 1 次不稳定）⇒ 编写席没法靠"改写法"绕过去。
- **要求**：作用域按**真实文件身份**判定、不要按目录前缀；判据必须**确定性**。

### B10 跨工作区写要人工批准 + 审批不流转到主对话（交接档 §18.3 P2）
- 账本里能核到的只有「**3 笔审批**」这个数（原文：跨两棵树写盘，期间宿主按操作弹了 3 次审批，用户已全部批准）；`approval:allowed-once` 字样在 `.pipeline` / `.dsh\sessions` / `.dsh\logs` 全量搜索中**一处都没有**。
- **要求**：给出**可核**的审批流转路径（谁的审批、流转到哪、留痕在哪）。

### B11 `sync-trees.cjs` 硬编码写区外那棵（交接档 §18.3 P3）
- 脚本本体：`T-20261011-5a871c\reports\writer\sync-trees.cjs`（5061 B）。第 20–21 行把 `ACTIVE`（生效副本）与 `SOURCE`（`dsh_orb\新任务-…\dsh-pipeline`，**区外**）写死；`--write` 时把生效副本里本单改动的 7 个文件逐个复制进源码树。
- **要求**：改成「**只写区内 + 输出待同步清单**」。

### B12 `pipeline_help` 工具不存在，但被引用
- **现象**：计划 AI 调 `pipeline_help` → `Error: unknown tool "pipeline_help"`。而插件里已有 `normify_help` 这类"按主题速查"的工具惯例。
- **要求**：要么实现它（插件自己的帮助 / 速查入口），要么把它从任何提示与文档里去掉。**二选一，不要留着悬空。**

### B13 计划的 `role_boundaries` 没有覆盖全部执行角色
- **现象**：派活回执自带警告「**计划里没有「需求分析」的边界卡（本应覆盖全部执行角色）—— 请让计划 AI 补上**」。实际 `orchestrator`、`architect`、`security`、`reviewer` 等在 `T-20261011-214043` 的计划里都缺卡。
- **要求**：计划工具应**强制** `role_boundaries` 覆盖清单里每一个执行角色（像 `forbidden` 至少 1 条那样硬性），而不是等到派活那一刻才提醒。

### B14 水位自报被播报成「交了一份交接物」
- **现象**：实测两条唤醒写「交了一份交接物」，账本无新文件；同期席位正在按 brief 调 `pipeline_context_report`（水位自报）。二者高度疑似同源。
- **要求**：播报类型与实际调用一致。
