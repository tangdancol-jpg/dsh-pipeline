## 三、"刷新即变"实证（追加 → 请求 → 还原）

对 `bug待修复单-20261014.md` 末尾追加一行无害标记
`<!-- 面板自验标记：2026-10-14T12:09:58.xxxZ -->`（56 B），请求一次，然后**截断还原**。

| 阶段 | 文件字节数 | 页面总字节数 | 页面数据源行（mtime / 字节数 / sha256 前 12） |
|---|---|---|---|
| **追加前** | **35,710 B** | 45,275 B | 2026-10-14 20:06:18 / 35,710 / **`800866e86b53`** |
| **追加后** | **35,766 B** | 45,275 B | 2026-10-14 20:09:58 / 35,766 / **`8ea3fd9a7c8c`** |
| **还原后** | **35,710 B** | 45,275 B | 2026-10-14 20:09:58 / 35,710 / **`800866e86b53`** |

**还原验证 ✓**：还原后文件 35,710 B，与追加前**逐字节相同**（`Buffer.compare = 0`），sha256 前 12 位回到 `800866e86b53`（与追加前一致）；文件内已无 `面板自验标记` 字样（`marker_present = False`）。

### 结论：面板**实时读盘，成立**（不是缓存实现）

三条独立证据：

1. **数据源行三个字段在同一轮请求里全变了** —— 追加后那次请求，页面上的 mtime（20:06:18→20:09:58）、字节数（35,710→35,766）、sha256（`800866e86b53`→`8ea3fd9a7c8c`）**同时**更新 ⇒ 该次请求真的重新 `stat` + 读全文 + 重算哈希。
2. **连发三次请求，"本次读取时刻"每次都推进** —— `20:10:22 → 20:10:24 → 20:10:25` ⇒ 页面每次请求重新生成，不是一份被缓存住的响应。
3. **服务端源码与响应头** —— `dashboard\server.mjs:95-117` 的 `readSources` 注释原文就是 `// ── 读数据源（★ 每次请求都现读）──`，函数体内每次 `fs.statSync` + `fs.readFileSync` + `crypto.createHash`；两条响应路径都设 `cache-control: no-store`。

### ★ 一个必须说清的坑：页面总字节数这个指标**不敏感**（假阴性）

页面总字节数三次都是 **45,275 B，完全没变**。若只看这一个数字，会得出"面板在缓存 ⇒ 缺陷"的**错误**结论。真实原因是两条同时成立：

- **(a) 追加的是一行 HTML 注释，落在文件末尾** —— 解析器按表格行取条目，注释不产出任何条目，所以页面**正文一个字节都没多**；
- **(b) 所有真变了的单元格都是定宽的** —— mtime `2026-10-14 20:06:18`→`20:09:58` 等长、字节数 `35,710`→`35,766` 等长、sha256 `64 位→64 位` 等长。

⇒ 所以"字节数不变"在这里是**假阴性**，判据应以 **mtime / sha256** 为准。本次硬约束只允许那一次追加+还原，因此没有改追加会让页面真的长字节的内容，而是用更硬的证据（数据源行三字段 + 读取时刻推进 + 源码 + 响应头）来判定 —— 这比字节数更可信。
