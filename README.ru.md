# dsh-pipeline — плагин конвейера многоагентного взаимодействия + встроенная панель управления
[中文](README.md) | [English (US)](README.en-US.md) | [日本語](README.ja.md) | **Русский**

`dsh-pipeline` — плагин конвейера многоагентного взаимодействия для DSH: основная беседа только
распределяет задачи и сама работу не выполняет, а роли написания / тестирования / проверки строго
разделены; выход за рамки полномочий, пропуск шагов и закрытие задачи без OK блокируются кодом до
выполнения инструмента. Плагин несёт **встроенную панель управления** — клиентская точка входа
`lib/client.js` при первом отображении панели подгружает 14 chunk-файлов `lib/client.panel-*.js` и
показывает справа в заголовке сессии состояние конвейера, места (seats) и предпросмотр сессии.
Этот репозиторий = исходный код плагина + документация для разработчиков + отчёты о поставке и схемы
(всё в `docs/`) + отдельная локальная страница только для чтения (`dashboard/`).

## 1. Развёртывание: clone → установка

```powershell
git clone <URL репозитория> dsh-pipeline
cd dsh-pipeline
powershell -NoProfile -ExecutionPolicy Bypass -File .\plugin\active\install.ps1 -DryRun   # сначала прогон без изменений
powershell -NoProfile -ExecutionPolicy Bypass -File .\plugin\active\install.ps1            # установка
```

Установщик только копирует и регистрирует: копирует рабочие файлы в
`<каталог DSH>\profiles\<profile>\node_modules\dsh-pipeline\`, добавляет регистрацию плагина в
`package.json` / `cordis.patch.yml` этого profile (с предварительным резервным копированием обоих) и
кладёт входящий в комплект Skill stop-ladder в `<каталог DSH>\skills\stop-ladder\`.

| Этап | Что получаете |
|---|---|
| **После clone** | Весь репозиторий: `plugin/active/` (исходники + `tests/` + `presets/` + `design/`), `docs/`, `dashboard/`, `MANIFEST.sha256`. |
| **Что установка кладёт в profile** | Только **рабочие файлы**: `index.js`, `lib/`, `locale/`, `skills/`, `presets/`, `icon.svg`, `package.json`, `cordis.patch.yml`, `README.md`, `ARCHITECTURE.md`, два `.ps1`, а также `tests/` (его читает `pipeline_selftest`). |
| **Что не устанавливается по умолчанию** | `docs/` и `dashboard/` в корне репозитория (установщик копирует только из `plugin/active/`), а также `design/`, `examples/`, `REPORT.md`, `tools/` внутри каталога плагина. Они скачиваются вместе с clone, просто не попадают в profile. |
| **Что добавляет только `-WithDocs`** | `examples/`, `REPORT.md`, `tools/` (по-прежнему внутри `plugin/active/`). |

Область копирования имеет ровно один источник: `plugin/active/tools/install-items.json` — его читают и
`install.ps1`, и `tools/sync*.mjs`, поэтому правка меняет три места сразу.

| Частый параметр | Значение |
|---|---|
| `-DryRun` | Только показать, что будет сделано; ничего не менять. |
| `-Profile <имя>` | В какой profile устанавливать; по умолчанию `desktop`. |
| `-WithDocs` | Дополнительно установить `examples/`, `REPORT.md`, `tools/`. |
| `-NoSpawnRoles` | Только выдать токены, не создавать сессии ролей (режим прогона без токенов). |

Полный набор параметров (`-ProjectRoot` / `-Transport` / `-GuardMainReadsCode` /
`-MaxReworkPerLeg` / `-L0OrchestratorSeparate` …), что именно меняет скрипт и как откатиться
(`rollback.ps1`) — в [`docs/install.md`](docs/install.md). После установки нужно **перезапустить
DSH** (или перезагрузить плагин), иначе работающий процесс продолжит использовать старый код.

## 2. Исходный код плагина: `plugin/active/`

### Структура модулей

Точка входа — `index.js`, реализация находится в `lib/`. Пять исходных файлов размером более тысячи
строк каждый разделены по темам на подкаталоги, а исходные файлы сохранены как фасады (имена экспорта
не изменились, поэтому вызывающему коду не нужно менять импорты):

| Фасад | Подкаталог | Содержимое |
|---|---|---|
| `lib/store.js` | `lib/store/` | Хранение задач: чтение и запись на диск, критерии хаба супервизора, предусловия переходов состояний, отправка передач, вмешательство человека… |
| `lib/tools.js` | `lib/tools/` | Определения инструментов `pipeline_*`, сгруппированные по инструментам |
| `lib/guard.js` | `lib/guard/` | Защита (guard): классификация прав чтения и записи ролей, места (seats) и область полномочий, критерии для shell, раскрытие скриптов, основное решение |
| `lib/handoff.js` | `lib/handoff/` | Передачи (handoff): таблица полей, проверка, сканирование содержимого, запись |
| `lib/wakeup.js` | `lib/wakeup/` | Пробуждение (wakeup): ключи пробуждения, идентичность журнала, доставка, механизм пробуждения |

Другие домены, разделённые по функциям:

| Каталог | Содержимое |
|---|---|
| `lib/panel/` | Встроенная панель: `snapshot.js` (снимок только для чтения) / `seats.js` (слияние мест из трёх слоёв) / `task-fields.js` (контракт полей и порядка ключей) / `actions.js` (8 действий записи) / `archive.js` (вид архива `_trash`) / `pins.js` (закрепления `_panel-pins.json`) |
| `lib/model/` | Доменные объекты: `task` / `baseline` / `artifact` / `close-report` / `human-request` / `handoff-*` (структура, значения по умолчанию, перечни полей) |
| `lib/errors/` | Единственный источник кодов ошибок (`codes.js`) и текстов отказов / подсказок (`text.js`) |
| `lib/transport/` | Интерфейс каналов и реализации: `session` / `team` / `subagent` / `manual` / `simulated`; `createTransport()` — единственная точка выбора |
| `lib/team/` | Адаптер официальных Agent Teams: именование, проверка канала, внедрение персоны роли, закрепление четырёх слотов, доставка, зеркалирование доски задач |
| `lib/states/` `lib/tiers/` `lib/guard/` и др. | Машина состояний, правила уровней, шлюзы… — всё разбито по принципу «один файл — одна причина изменения» (см. `CONVENTIONS.md` §4) |

Номера строк вида `lib/store.js:2471` в отчётах в `docs/` относятся к единому файлу до разделения.
Текущее расположение следует искать в соответствующем коде в `lib/` текущего дерева исходников.

### Клиент: одна точка входа + 14 chunk

Браузерная половина — не один большой файл: точка входа занимает 400 строк (ровно предел), а
реализация панели разделена на 14 chunk.

| Файл | Строк | Ответственность |
|---|---|---|
| `lib/client.js` | 400 (предел 400) | Точка входа: регистрация модуля, переключатель «мульти-AI координация» (order 100), lazy wrapper панели (order 110 — chunk берутся только при первом отображении) |
| `lib/client.panel-*.js` ×14 | каждый ≤ 400 | Реализация панели: `shell` / `view` / `atoms` / `data` / `seats` / `menu` / `batch` / `batch-bar` / `card-actions` / `actions` / `preview` / `preview-data` / `preview-control` / `preview-bubble` |

Как это загружается (три этапа; протокол chunk нативно предоставляет хост-пакет
`@deepseek-ai/dsh-client-modules`):

1. **Точка входа**: хост загружает `/plugins/dsh-pipeline/client.js?rev=<rev точки входа>` как **классический
   скрипт** (без `import` / `export` / top-level `await`), и точка входа сама регистрируется через
   `window.__ModuleLoader__.load({ id, factory })`.
2. **Chunk по требованию**: при **первом отображении** панели точка входа выполняет
   `Promise.all(require.async('./client.panel-*.js'))`, параллельно забирает все 14 chunk и передаёт
   их `shell`, который собирает панель через `create(deps)` в порядке зависимостей — если панель ни
   разу не открывали, ничего не скачивается.
3. **Как отдаёт хост**: chunk приходят с `/plugins/dsh-pipeline/<chunk>?rev=<rev точки входа>`; хост
   читает файл асинхронно по требованию и **кэширует как immutable** (повторно — только при смене
   `rev`). Chunk должен лежать **в том же каталоге, что и точка входа**, и тоже быть классическим
   скриптом; регистрируется через `window.__ModuleLoader__.load({ id, chunk, factory })`. Chunk
   **не могут** синхронно `require` друг друга — сборка происходит только в точке входа.

Протокол — «точка входа + соседние файлы», поэтому достаточно обычного рукописного JS: **ни tsdown,
ни правки `package.json` не нужно**. Новая клиентская логика всегда начинается новым chunk (точка
входа уже на пределе 400 строк); обоснование и границы — в
[`plugin/active/CONVENTIONS.md`](plugin/active/CONVENTIONS.md) §4.

node tests\<набор>.mjs            # запустить один набор

  оттуда. Если критерий недоступен, это явно помечается «пропущено, не входит в процент прохождения».
  На этой машине: с `DSH_APP_ASAR` — 3668/3668; без него 3 проверки пресетов красные (это особенность
  окружения, а не дефект кода).
- `tests/seat-liveness-wake-check.mjs` не зарегистрирован в полном наборе, а его содержимое устарело
  относительно нынешних критериев потери связи, поэтому при отдельном запуске он падает.

## 3. Панель управления

### Встроенная панель (справа в заголовке сессии)

Монтируется в `conversation.session.header.utilities` (list-слот), рядом с переключателем
«мульти-AI координация»:

- **Бейдж уровня**: крайний слева на каждой карточке задачи — бейдж уровня `L0`–`L5` и размер
  команды (`N AI`), чтобы сразу видеть, насколько тяжёлая задача.
- **Меню ⋯**: по состоянию показывает «остановить / восстановить / архивировать / удалить»; удаление
  требует второго клика для подтверждения.
- **Закрепление**: 📌 закрепить / открепить; закреплённые задачи идут первыми, остальные — по
  `updated_at` по убыванию.
- **Пакетный режим**: «Пакетно» в заголовке → отметить несколько карточек → нижняя панель предлагает
  «архивировать выбранные / удалить выбранные», выполняется последовательно с показом прогресса.
- **Вид архива**: «Архив N» в заголовке показывает архивированные задачи; в строке доступны
  «восстановить» или «удалить навсегда» (второе — по второму клику); «← к задачам» возвращает назад.
- **Предпросмотр сессии при наведении**: наведение на чип места открывает слева от панели окно
  предпросмотра примерно 520×520 (до 12 строк, с прокруткой). Показывается только **реальный диалог
  пользователя / AI** (внедрённый системный контекст и строки инструментов отфильтрованы); пока у AI
  нет текста, показывается «думает…»; **клик по любому пузырю открывает эту сессию** (`openSession`).

Чтение и запись — два разных пути:

| Назначение | Маршрут | Контракт |
|---|---|---|
| Чтение | `GET /.dsh-pipeline/panel` | Снимок только для чтения, опрос каждые 5 с и пропуск, пока страница скрыта; читаются только структурные поля `task.json` (id / состояние / краткое требование / места / число ожидающих людей / номер доски задач / уровень / закрепление / `allowed_actions`), **никогда** тела передач, патчи или код |
| Чтение (архив) | `GET /.dsh-pipeline/panel?view=archived` | Список архивированных задач в `<корень проекта>/.pipeline/_trash/`, только чтение |
| Запись | `POST /.dsh-pipeline/panel/action` | 8 действий: `cancel` / `restore` / `archive` / `delete` / `pin` / `unpin` / `unarchive` / `delete_archived`; при выключенном переключателе отклоняются все; `delete` / `delete_archived` требуют `confirm: true`; принимается только same-origin JSON |

Куда пишется (всё в `.pipeline/` рабочей области, поэтому следует за profile): закрепления —
`_panel-pins.json`, архив — `_trash/<id задачи>-<метка времени>/`, надгробия безвозвратного удаления —
`_purge-log.jsonl`. Компромиссы проектирования и контракты полей — в
[`plugin/active/design/panel/01-面板设计.md`](plugin/active/design/panel/01-面板设计.md).

### Отдельная страница только для чтения `dashboard/`

`dashboard\start.cmd` / `dashboard\stop.cmd`; подробности — в

## 5. Проверка

`MANIFEST.sha256` — это sha256 каждого отслеживаемого файла, кроме самого себя. Выполните в корне
репозитория:

```bash
sha256sum -c MANIFEST.sha256
```

После изменения файлов его нужно перегенерировать (точные правила и альтернативная команда для
Windows — в [`docs/manifest.md`](docs/manifest.md)).
